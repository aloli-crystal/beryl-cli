= beryl — Guide de test grandeur nature
:toc: left
:toc-title: Table des matières
:toclevels: 3
:source-highlighter: rouge
:icons: font

Ce document décrit la procédure de test réel du bootstrap beryl :
d'abord en local dans une VM UTM, puis sur des serveurs OVH et Scaleway.

[WARNING]
====
Le bootstrap beryl est **destructif** : il efface intégralement le disque
cible. N'exécutez ces tests que sur des machines explicitement dédiées aux
tests et ne contenant *aucune* donnée à conserver.
====

== Pré-requis locaux

* Un Mac avec https://mac.getutm.app/[UTM] installé (gratuit, libre).
* Le binaire beryl compilé : `shards build` à la racine du projet.
* Une paire de clés SSH utilisable (`~/.ssh/id_ed25519` par défaut).

== 1. Test local avec UTM

=== 1.1 Préparer la VM « rescue Linux »

L'objectif est de reproduire ce que fournissent OVH ou Scaleway :
un environnement Linux minimal avec SSH actif et un disque vide à côté.

. Créer une VM UTM (Apple Silicon) :
  * Architecture : *x86_64* (pour simuler un dédié standard) ou *aarch64* pour un test ARM natif plus rapide.
  * RAM : *2 Go* minimum.
  * Disque : *20 Go* minimum (le disque sur lequel beryl écrira mfsBSD, puis FreeBSD).
  * Réseau : *Shared Network* ou *Bridged* (pour pouvoir SSH depuis le Mac).

. Booter sur une ISO Debian 12 ou Ubuntu 24.04 *live* (pas installée) :
  * https://www.debian.org/CD/live/ pour Debian.
  * Lors du boot, choisir « Try without installing » ou équivalent.

. Configurer SSH dans le live :
+
[source,sh]
----
sudo passwd root                         # définit un mot de passe temporaire
sudo sed -i 's/^#\?PermitRootLogin.*/PermitRootLogin yes/' /etc/ssh/sshd_config
sudo systemctl restart ssh
----

. Déposer votre clé publique :
+
[source,sh]
----
mkdir -p /root/.ssh
echo "votre-clé-publique-ici" > /root/.ssh/authorized_keys
chmod 600 /root/.ssh/authorized_keys
----

. Noter l'IP attribuée à la VM (`ip -4 addr show` dans la VM).

=== 1.2 Déclarer la VM dans l'inventaire

Créer `inventory.yml` à la racine du projet :

[source,yaml]
----
defaults:
  user: root
  identity_file: ~/.ssh/id_ed25519

hosts:
  utm-test.local:
    provider: generic
----

Remplacer `utm-test.local` par l'IP ou un nom présent dans `/etc/hosts`.

=== 1.3 Identifier le disque cible

Depuis le Mac, se connecter manuellement à la VM pour vérifier le nom du disque :

[source,sh]
----
ssh root@utm-test.local "lsblk -dno NAME,TYPE,SIZE | awk '\$2==\"disk\"'"
----

Attendu : `sda  disk  20G` (ou `vda`, `nvme0n1`, selon UTM).

=== 1.4 Lancer le bootstrap

[source,sh]
----
./bin/beryl bootstrap utm-test.local --disk=/dev/sda
----

Le nouveau flux (ADR-011, QEMU-in-rescue) ne fait plus de `dd` direct
sur le disque : il lance une VM QEMU *depuis le rescue Linux* avec le
disque réel en passthrough, et laisse `bsdinstall` écrire une FreeBSD
nativement UEFI-bootable.

Étapes observables (sur stderr) :

. Vérification Linux (uname).
. Installation `qemu-system-x86`, `ovmf`, `xorriso` dans le rescue (apt).
. Téléchargement de `FreeBSD-15.0-RELEASE-amd64-disc1.iso` (~1 Go) —
  réutilisée si déjà présente dans `/root/beryl-test/`.
. Remasterisation de l'ISO via `xorriso` pour y insérer
  `/etc/installerconfig` (script `bsdinstall` non interactif).
. Copie de `OVMF_VARS_4M.fd` pour donner à QEMU un état UEFI modifiable.
. Lancement de QEMU (UEFI via OVMF, `-enable-kvm`, `-machine q35`,
  disque réel en virtio passthrough, `-no-reboot`).
. `bsdinstall` tourne à l'intérieur de la VM : partitionnement ZFS,
  distribution pkgbase, users `admin` + `deploy`, clé SSH posée,
  `rc.conf` (ifconfig_DEFAULT), `fstab` (labels GPT), timezone.
. Au `poweroff` final, QEMU quitte proprement (-no-reboot).
. `reboot -f` du rescue → l'UEFI bare metal trouve la FreeBSD posée.
. Attente SSH sur le système installé en tant que `admin`.

Durée totale typique : **25 à 35 min**. La plus grosse partie va dans
le téléchargement de l'ISO (première passe seulement) et dans
`bsdinstall` (pkgbase).

=== 1.5 Vérifications

Le FreeBSD installé pose `PermitRootLogin no` par défaut : on se
connecte en tant que `admin` (qui est dans le groupe `wheel` avec
`sudo NOPASSWD`).

[source,sh]
----
ssh -o StrictHostKeyChecking=no admin@utm-test.local << 'EOF'
  uname -srm
  hostname
  sudo zpool list
  sudo zfs list
  pkg info | head -20
  cat /etc/rc.conf
  id deploy
EOF
----

Attendu :

* `uname -srm` → `FreeBSD 15.0-RELEASE amd64`.
* `zpool list` → pool `zroot` en ligne.
* `pkg info` → `sudo`, `zsh`, `chruby`, `ruby-install` en plus de la base.
* `id deploy` → user `deploy` dans le groupe primaire `www` (pas `wheel`).

== 2. Test OVH dédié

Depuis ADR-011 (20 avril 2026), le flux n'a plus besoin de `beryl
prep-rescue`, ni de craindre le `dd` bare metal : tout passe par une
VM QEMU lancée dans le rescue Linux. On arrive donc avec un rescue
Debian fonctionnel, on lance `beryl bootstrap <host>` et on va boire
un café — 25 à 35 min plus tard, FreeBSD répond en SSH.

=== 2.1 Provisionner un serveur

Deux chemins possibles, selon l'état actuel du serveur :

==== 2.1.a Debian/Ubuntu déjà installé via l'installateur OVH

Si vous (ou un précédent opérateur) avez installé Debian ou Ubuntu
depuis le manager OVH et que votre clé SSH publique était déclarée
sur votre compte OVH au moment du provisioning, elle est **déjà
présente** dans `/root/.ssh/authorized_keys` — vous pouvez vous
connecter directement :

[source,sh]
----
ssh root@<IP> uname -a
----

Dans ce cas `beryl prep-rescue` n'est **pas utile** (la clé est déjà
posée). Passez directement à la section « Inventaire » ci-dessous.

[IMPORTANT]
====
**Vérifiez quelle clé est posée côté serveur** et utilisez *la même*
localement. Si votre `~/.ssh/id_ed25519` local ne correspond pas à la
clé déclarée sur le compte OVH au moment du provisioning, la connexion
échouera malgré tout.

Côté serveur :

[source,sh]
----
ssh root@<IP> "cat /root/.ssh/authorized_keys"
----

Côté poste local :

[source,sh]
----
for p in ~/.ssh/*.pub; do
  echo "=== $p ==="; cat "$p"
done
----

Si la clé attendue n'est pas `~/.ssh/id_ed25519`, précisez-la dans
votre inventaire (`identity_file:`) ou dans `~/.ssh/config`.
====

[NOTE]
====
En théorie seulement : OVH n'installe la clé que si elle était
associée à votre compte *au moment de l'installation*. Si vous l'avez
ajoutée après coup, ou si l'image utilisée ne supporte pas cloud-init,
il faut la poser manuellement via `beryl prep-rescue` ou `ssh-copy-id`.
====

==== 2.1.b Mode rescue OVH (serveur sans clé accessible)

Si aucun SSH ne répond (serveur neuf, reinstallation en cours, etc.) :

. Depuis le manager OVH, activer le mode rescue :
  * Menu *Serveur dédié → Netboot → Rescue (rescue64-pro)*.
  * Redémarrer le serveur.

. OVH envoie par mail les credentials (IP + mot de passe root temporaire).
. Déposer votre clé publique — deux méthodes :
+
[source,sh]
----
# Méthode 1 : ssh-copy-id classique (votre poste doit pouvoir atteindre <IP>)
ssh-copy-id root@<IP>        # entrer le mot de passe reçu

# Méthode 2 : beryl prep-rescue (utile si le copier-coller est bloqué
# sur un accès console/KVM hors-bande, voir section test local UTM).
./bin/beryl prep-rescue --bind 0.0.0.0
# puis, dans le rescue : curl -fL http://<IP_poste>:8080/s | sh
----

=== 2.2 Inventaire

[source,yaml]
----
hosts:
  test-ovh.aloli.fr:
    provider: ovh
    # Pointe vers l'IP OVH ; ajoutez une entrée /etc/hosts si besoin
    # ou remplacez la clé du hash par l'IP.
----

=== 2.3 Identifier le disque

[source,sh]
----
ssh root@test-ovh.aloli.fr "lsblk -dno NAME,TYPE,SIZE"
----

Les serveurs OVH sont souvent en NVMe : attendu `nvme0n1  disk  500G`.
Si deux disques (configuration RAID), la v1 de beryl n'en prend qu'un.

=== 2.4 Bootstrap

[source,sh]
----
./bin/beryl bootstrap test-ovh.aloli.fr --disk=/dev/nvme0n1
----

C'est la seule commande à lancer. Pas de `beryl prep-rescue`,
pas de phase intermédiaire mfsBSD. Ouvrez la console KVM/IPMI
du manager OVH en parallèle pour observer les phases visibles
sur l'écran :

. BIOS/UEFI du bare metal (début et fin du flux).
. Prompt du rescue Linux Debian (pendant que beryl tourne côté
  rescue, 25-35 min).
. Écran de boot FreeBSD 15 via UEFI (après le reboot final).
. Prompt `login:` FreeBSD 15 (= fini, SSH doit répondre en `admin`).

Entre ces points, QEMU tourne en mode `-nographic` — il n'y a rien à
l'écran côté KVM pendant ~20 min. C'est normal. La sortie série de la
VM QEMU est capturée dans `/root/beryl-test/qemu-serial.log` côté
rescue (utile si le bootstrap échoue).

=== 2.5 Filet de sécurité

Si le premier boot FreeBSD échoue (pas de SSH au bout de 30 min) :

. Repasser en mode rescue OVH depuis le manager et récupérer
  `/root/beryl-test/qemu-serial.log` qui contient toute la sortie
  série de la VM : partitionnement, install pkgbase, post-install
  chroot, poweroff.
. Diagnostiquer via la console KVM OVH si l'UEFI ne trouve plus rien
  (Secure Boot activé ? ordre de boot ? ESP non détectée ?).
. Relancer `beryl bootstrap` — le flux est idempotent : l'ISO est
  re-téléchargée seulement si absente, et `bsdinstall` réécrit tout
  le disque.

== 3. Test Scaleway Dedibox

=== 3.1 Provisionner

Comme pour OVH (section 2.1), deux chemins :

==== 3.1.a Ubuntu/Debian déjà installé via l'installateur Scaleway

Si un OS a été installé depuis la console Scaleway avec votre clé SSH
publique déclarée sur le compte, elle est **déjà** dans
`/root/.ssh/authorized_keys`. `beryl prep-rescue` n'est alors **pas
utile**. Vérifiez :

[source,sh]
----
ssh root@<IP> uname -a
----

Attention (comme pour OVH) à utiliser la *même* clé localement que
celle posée sur le serveur — sinon la connexion échouera malgré tout
(voir la section 2.1.a « IMPORTANT » pour la procédure de vérification
côté serveur et côté poste local).

==== 3.1.b Mode rescue Scaleway

. Console Scaleway → *Mon compte → Serveur → Rescue*.
. Choisir le rescue Ubuntu, rebooter.
. Récupérer les credentials par mail.
. Déposer votre clé publique avec l'une des deux méthodes :
+
[source,sh]
----
# classique :
ssh-copy-id root@<IP>

# ou, si copier-coller bloqué côté console :
./bin/beryl prep-rescue --bind 0.0.0.0
# dans le rescue : curl -fL http://<IP_poste>:8080/s | sh
----

=== 3.2 Inventaire

[source,yaml]
----
hosts:
  test-scaleway.aloli.fr:
    provider: scaleway
----

=== 3.3 Bootstrap

[source,sh]
----
./bin/beryl bootstrap test-scaleway.aloli.fr --disk=/dev/sda
----

Comme pour OVH (section 2.4), c'est la seule commande à lancer. Le
flux `QEMU-in-rescue` tourne pendant 25-35 min puis le serveur
redémarre sur FreeBSD. SSH ensuite en tant que `admin`.

Si le rescue Scaleway n'a pas `apt` (variantes non-Debian), il faudra
choisir un rescue Ubuntu depuis la console pour que
`beryl bootstrap` puisse poser `qemu-system-x86`, `ovmf` et `xorriso`.

=== 3.4 Console

En cas de problème, accéder à la console série Scaleway depuis le panneau
de contrôle (KVM IPMI sur certaines gammes).

== 4. Capture et partage pour diagnostic collaboratif

Quand un test échoue ou qu'on veut revoir exactement ce qu'il s'est
passé, la qualité du diagnostic dépend de ce qui a été capturé pendant
le run. Voici le setup recommandé — particulièrement utile pour un
debug à deux (opérateur + contributeur / mainteneur à distance).

=== 4.1 Formats utiles

[cols="1,2,1"]
|===
| Type | Usage | Exploitable à distance ?

| Vidéo MP4
| Archive visuelle, preuve, démos
| Limité — impossible à ingérer automatiquement ; utile si l'autre
  partie peut la visionner.

| Capture terminal (`script -t` ou `asciinema rec`)
| Enregistre *toutes* les commandes tapées et leurs sorties, en texte
  rejouable
| *Idéal* : chaque ligne peut être lue et citée dans un échange écrit.

| Screenshots console KVM/IPMI
| Capture l'écran du serveur *hors-bande* (utile aux moments où SSH
  n'est plus joignable : reboot, boot mfsBSD, boot FreeBSD)
| *Très utile* pour les phases post-reboot.

| Fichier log série QEMU (`/root/beryl-test/qemu-serial.log`)
| Capture côté rescue de toute la sortie série de la VM QEMU pendant
  `bsdinstall` : partitionnement, pkgbase, post-install chroot, poweroff.
| *Utile après coup* pour reconstituer une phase qui a échoué dans QEMU.

| Sortie `dmesg`, `journalctl -b`
| Messages kernel et systemd pour les échecs bas niveau (drivers,
  montage ZFS, etc.)
| Utile quand le boot ne va même pas jusqu'au rc.conf.
|===

=== 4.2 Setup recommandé avant un test

Dans le terminal sur le poste opérateur, avant de lancer beryl :

[source,sh]
----
cd ~/prod-crystal/beryl
mkdir -p tmp # dossier non suivi par git pour les artéfacts
script -q -t 2>tmp/beryl-timing.txt tmp/beryl-session.log
# une nouvelle session shell s'ouvre, tout est enregistré
----

Ensuite, dans cette session enregistrée, exécuter la séquence de test
normale :

[source,sh]
----
./bin/beryl -i inventory.yml list-hosts
./bin/beryl -i inventory.yml show <host>
./bin/beryl -i inventory.yml bootstrap <host> --disk=/dev/nvme0n1
----

Quand la session est finie (réussite ou échec), sortir de script :

[source,sh]
----
exit
----

Le fichier `tmp/beryl-session.log` contient tout (commandes + sorties).
Si besoin de le partager, il est en `tmp/` donc non versionné — vous
pouvez le coller dans un gist, un fichier attaché à une issue, ou
directement dans un chat.

Alternative `asciinema` (rendu plus agréable, animation possible) :

[source,sh]
----
brew install asciinema
asciinema rec tmp/beryl-session.cast
# ... commandes beryl ...
# Ctrl+D pour arrêter
asciinema play tmp/beryl-session.cast
----

=== 4.2.bis KVM / IPMI hors-bande

Quand le serveur ne boote pas et SSH ne répond pas, la console KVM
hors-bande (IPMI, iKVM, Intel vPro) est **indispensable** pour voir
ce que l'UEFI/BIOS affiche : écran d'erreur, loop PXE, prompt bootloader,
kernel panic…

==== Sur Apple Silicon

Les JNLP Supermicro/ASPEED d'OVH chargent une `.dylib` native
(`iKVM64.dylib`) compilée en x86_64 uniquement. Java arm64 natif refuse
de la charger (`no iKVM64 in java.library.path`). Solution :

[source,sh]
----
brew install --cask openwebstart
----

https://openwebstart.com/[OpenWebStart] remplace `javaws` (retiré depuis
Java 11) et bootstrape un JDK x86_64 sous Rosetta à la demande. Après
installation, double-cliquer le `.jnlp` téléchargé → fenêtre KVM.

Alternative manuelle (si OpenWebStart pose problème) :

[source,sh]
----
arch -x86_64 brew install --cask temurin8
arch -x86_64 /Library/Java/JavaVirtualMachines/temurin-8.jdk/Contents/Home/bin/java \
  -jar /chemin/vers/ikvm-launch.jar
----

=== 4.3 Screenshots console à prendre

Quand beryl atteint ces messages, ouvrir la console KVM/IPMI de
l'hébergeur et capturer l'écran :

* `[beryl bootstrap qemu-in-rescue] 7/8 — redémarre le bare metal`
  → capture au moment du reboot (confirme que le rescue a bien fermé
  et laissé la place au firmware UEFI).
* `[beryl bootstrap qemu-in-rescue] 8/8 — attend le retour SSH sur le FreeBSD installé`
  → capture de l'écran de boot FreeBSD 15 via UEFI (confirme que
  `loader.efi` + noyau ont été trouvés par le firmware).
* En cas de timeout : capturer l'écran courant, il montre souvent
  l'erreur (kernel panic, mountroot prompt, PXE loop, etc.).

=== 4.4 Logs internes à récupérer (si accessible en SSH)

Pendant que QEMU tourne (rescue Linux accessible en SSH) :

[source,sh]
----
# sur le rescue, pour suivre l'install en direct :
tail -f /root/beryl-test/qemu-serial.log
----

Une fois connecté en SSH au système installé (`admin@<host>`) :

[source,sh]
----
uname -srm
sudo dmesg | tail -100
sudo cat /var/log/messages | tail -200
sudo zpool status
sudo zfs list
pkg info | head -30
cat /etc/rc.conf
----

Copier ces sorties dans la session `script` enregistrée — elles feront
partie du log partagé.

=== 4.5 Checklist pré-test

Avant de lancer `beryl bootstrap`, vérifier :

* [ ] Clé SSH en local : `ssh-add -l` montre la clé ou un agent dispo.
* [ ] Inventaire prêt : `./bin/beryl list-hosts` affiche bien l'hôte cible.
* [ ] Accès SSH ok : `./bin/beryl show <host>` puis `ssh root@<host> uname -a`.
* [ ] Disque identifié : `ssh root@<host> "lsblk -dno NAME,TYPE,SIZE"` → noter le bon `/dev/...`.
* [ ] Filet de sécurité : savoir comment repasser en rescue via le panel hébergeur si besoin.
* [ ] Binaire beryl à jour : `git pull && shards build` sur le poste opérateur.
* [ ] Session `script` ou `asciinema` lancée.

=== 4.6 Quoi partager ensuite

Pour un diagnostic rapide à deux, coller ou attacher :

. `tmp/beryl-session.log` (ou le fichier `.cast` asciinema) — la session complète.
. 2-3 screenshots console KVM aux moments clés (surtout si SSH n'a jamais répondu).
. Un résumé en une phrase de l'étape où ça a coincé.

C'est largement suffisant pour démarrer l'enquête, sans avoir à rejouer
tout le test ensemble.

== 5. Reboot en rescue par API

Depuis la v0.2.0 des shards `aloli-crystal/api-ovh` et `aloli-crystal/api-scaleway`, `beryl` sait
basculer un hôte en mode rescue *sans passer par le manager web* :

[source,sh]
----
beryl rescue loulou.aloli.fr           # 1. l'hôte repart en rescue
beryl bootstrap loulou.aloli.fr \      # 2. on installe FreeBSD par-dessus
  --disk /dev/sda
----

L'étape 1 remplace l'aller-retour « clic dans le panneau → attendre le
mail de credentials → ssh avec mot de passe » par un appel API unique.

=== 5.1 Variables d'environnement à exporter

Pour OVH (trois crédentials à générer sur
https://api.ovh.com/createToken/) :

[source,sh]
----
export OVH_APPLICATION_KEY=...
export OVH_APPLICATION_SECRET=...
export OVH_CONSUMER_KEY=...
# Optionnel, défaut = eu :
# export OVH_ENDPOINT=eu    # ou ca, us, kimsufi_eu…
----

Pour Scaleway (une seule clé IAM depuis
https://console.scaleway.com/iam/api-keys) :

[source,sh]
----
export SCW_SECRET_KEY=...
export SCW_DEFAULT_ZONE=fr-par-2           # optionnel, défaut : fr-par-2
# export SCW_DEFAULT_PROJECT_ID=...        # pas requis pour le rescue
----

=== 5.2 Champs d'inventaire

Chaque hôte qu'on veut piloter par API doit porter un bloc au nom du
provider avec les identifiants exposés par l'hébergeur :

[source,yaml]
----
hosts:
  loulou.aloli.fr:
    provider: ovh
    ovh:
      service_name: ns3156789.ip-51-83-6.eu    # « Nom du service » OVH
      ssh_key_name: philippe-aloli-fr          # nom dans /me/sshKey

  mysrv-scw.aloli.fr:
    provider: scaleway
    scaleway:
      zone: fr-par-2
      server_id: 11111111-2222-3333-4444-555555555555
----

NOTE: `ssh_key_name` côté OVH doit *exister* dans le compte avant le
`beryl rescue`. Passer par `client.ssh_keys.create` du shard
`aloli-crystal/api-ovh` ou par le manager web. Côté Scaleway, les clés sont
ré-injectées automatiquement depuis celles posées à la création du
serveur : rien à déclarer dans l'inventaire beryl.

=== 5.3 Flux observé

[source,sh]
----
$ beryl rescue loulou.aloli.fr
[beryl rescue] OVH : prepare_rescue pour ns3156789.ip-51-83-6.eu (clé : philippe-aloli-fr)
[beryl rescue] OVH : tâche #42 (hardReboot) en todo
[beryl rescue] attente du retour SSH sur loulou.aloli.fr (port 22, user root, timeout 10 min)
[beryl rescue] ready : SSH répond sur loulou.aloli.fr
$ beryl bootstrap loulou.aloli.fr --disk /dev/sda
…flux QEMU-in-rescue habituel, 25-35 min…
----

Côté OVH, `beryl` enchaîne sous le capot : `GET /boot` → filtre le
`bootType == "rescue"` UEFI-compatible → `PUT` `bootId` → `POST
rescueSshKey` → `POST /reboot`. Côté Scaleway, un seul appel
`POST /servers/{id}/reboot` avec `boot_type: "rescue"` suffit.

=== 5.4 Options utiles

[cols="1,2"]
|===
| Option | Rôle

| `--timeout=MIN`
| Délai d'attente maximum du retour SSH (défaut : 10 minutes).

| `--no-wait`
| Retour immédiat après l'appel API, sans attendre SSH. Pratique pour
  lancer plusieurs rescues en parallèle puis attendre à la main, ou
  pour enchaîner depuis un autre outil.
|===

=== 5.5 Quand préférer le chemin manuel

* Serveur *non-OVH / non-Scaleway* (Hetzner, générique, VM UTM) :
  `beryl rescue` refusera avec `EXIT_BAD_PROVIDER`. Passer par le
  panneau de l'hébergeur et `beryl prep-rescue` comme avant.
* Rescue *sans API publique* (gammes anciennes, comptes partagés
  sans droit IAM) : idem, chemin manuel.
* Premier test de bout en bout : faire tourner une fois en manuel pour
  valider que l'hôte répond correctement, puis automatiser via `beryl
  rescue`.

== 6. Résolution des pannes

=== QEMU refuse de démarrer côté rescue

Causes typiques :

* CPU sans VT-x/AMD-V (rare en dédié moderne, possible sur du cloud).
  `beryl` s'appuie sur `-enable-kvm` qui échoue sans virtualisation
  matérielle. Vérifier côté rescue : `egrep -c '(vmx|svm)' /proc/cpuinfo`.
* Rescue non-Debian-like sans `apt` : `qemu-system-x86`, `ovmf` et
  `xorriso` ne seront pas installables automatiquement. Basculer sur
  un rescue Debian/Ubuntu.
* ISO corrompue ou tronquée dans `/root/beryl-test/disc1.iso` : supprimer
  le fichier et relancer, beryl re-téléchargera.

=== `bsdinstall` a échoué dans la VM

Symptôme : `beryl` sort en timeout sur la phase 8/8 (attente SSH
FreeBSD), ou QEMU quitte avec un code non nul avant le `poweroff`.

. Se reconnecter au rescue Linux (il doit encore être là, beryl n'a pas
  lancé `reboot -f` tant que QEMU tourne).
. Lire `/root/beryl-test/qemu-serial.log` : toute la sortie série de la
  VM est capturée, depuis le boot UEFI OVMF jusqu'au `poweroff`.
. Corriger (par exemple `installerconfig` mal rendu — auquel cas le
  template côté beryl doit être retouché) et relancer `beryl bootstrap`.

=== UEFI ne trouve rien à amorcer après le reboot final

Symptôme : `bsdinstall` a terminé proprement dans la VM (log série
clair), mais l'UEFI du bare metal retombe dans PXE ou un menu de boot
vide.

. Vérifier côté manager que Secure Boot est désactivé (OVH/Scaleway
  ont des options dans le BIOS netboot).
. Vérifier que l'ESP est bien sur le même disque que celui passé à
  `--disk` (pas de confusion NVMe0/NVMe1 sur machine à deux disques).
. Forcer l'ordre de boot UEFI sur le disque passé (certains firmwares
  privilégient la NIC par défaut).

=== Réinitialiser complètement

Repasser en mode rescue et relancer `beryl bootstrap` : `bsdinstall`
écrase intégralement la table de partition + ZFS.

== 7. Résultats attendus pour la v0.1

À l'issue du bootstrap, le serveur doit :

* [ ] Démarrer automatiquement sur FreeBSD 15 via UEFI sans intervention.
* [ ] Répondre en SSH sur le port 22 en `admin` (avec votre clé).
* [ ] Refuser `root` en SSH (défaut FreeBSD 15 `PermitRootLogin no`).
* [ ] Avoir un pool ZFS `zroot` en ligne.
* [ ] Avoir le hostname configuré.
* [ ] Avoir DHCP sur l'interface principale via `ifconfig_DEFAULT`
  (survit au changement de nom de NIC entre VM QEMU et bare metal).
* [ ] Avoir `deploy` créé dans le groupe primaire `www` (pas `wheel`).
* [ ] `sudo -n true` en tant qu'`admin` (wheel NOPASSWD).

Ce qui **n'est pas encore couvert** (Phase 2) :

* Durcissement SSH complet (profil Mozilla Modern).
* Services applicatifs (nginx, PostgreSQL, etc.).
* Alerting (dma, ntfy).

Ces aspects seront ajoutés après validation du bootstrap sur les trois
environnements (UTM, OVH, Scaleway) et leur retour d'expérience.
