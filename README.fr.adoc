= Beryl
:title-page:
:toc: left
:toc-title: Table des matières
:toclevels: 3
:source-highlighter: rouge
:icons: font

Outil Crystal de provisionnement FreeBSD, agentless SSH, multi-société et multi-fournisseur.
Bascule un serveur bare-metal OVH, Scaleway ou Dedibox en rescue Linux, installe FreeBSD 15
via mfsBSD-in-QEMU, puis applique une configuration déclarative à partir d'un arbre YAML.

Version courante : *0.1.41* (24 avril 2026). +
Dépôt : https://github.com/aloli-crystal/beryl +
Licence : MIT (voir section en bas de page).

[NOTE]
====
Beryl se place *avant* https://github.com/aloli-crystal/deploy[deploy] :
il prépare le serveur FreeBSD (OS, users, paquets système, clés SSH, durcissement sshd),
puis deploy déploie les applications Marten ou Kemal par-dessus.
====

== Vue d'ensemble

Les hébergeurs OVH, Scaleway et Online.net/Dedibox ne proposent pas FreeBSD comme image
native. La procédure manuelle — KVM-over-IP, image ISO custom, bascule à la main en
rescue — n'est ni reproductible ni automatisable. beryl automatise le cycle complet
*depuis le poste de l'opérateur* :

. `beryl init <société>` crée l'arborescence `~/.config/beryl/<société>/` (ADR-014).
. `beryl add-provider <société>/<provider>` enregistre les credentials API dans
  `~/.config/beryl/.env.yml` (chiffrés hors du dépôt).
. `beryl add-domain <société>/<domaine>` déclare la zone DNS, le fournisseur par
  défaut, les clés SSH des utilisateurs.
. `beryl rescue <host>` déclenche l'API hébergeur pour rebooter en rescue Linux,
  puis attend le retour SSH.
. `beryl scan <host> --dns --apply --hostname=<court>` se connecte au rescue,
  détecte les disques (lsblk -b -d), pose les records DNS A/AAAA et PTR, et
  écrit un `<host>.yml` prêt à bootstrapper.
. `beryl wipe <host>` efface les pools ZFS et partitions résiduels.
. `beryl bootstrap <host>` lance une VM mfsBSD *dans* le rescue (via QEMU) et
  installe FreeBSD 15 sur les disques déclarés (ADR-012/013 : post-install hors chroot).
. `beryl follow-install <host>` suit en direct le `bsdinstall.log` de la VM mfsBSD.
. `beryl apply <host>` synchronise la config effective (packages, users, clés SSH,
  sudoers) avec le serveur FreeBSD bootstrappé — travail en cours, pour l'instant
  limité au cycle bootstrap-only.

=== Architecture multi-société (ADR-014)

La configuration vit dans `~/.config/beryl/` organisée par société puis par domaine :

[source,text]
----
~/.config/beryl/
├── _default.yml                 # socle FreeBSD (timezone, users admin/deploy, packages)
├── .env.yml                     # credentials par société × provider (0600)
├── initech/                       # une société
│   ├── _account.yml             # métadonnées (nom complet, contact)
│   ├── initech.example.yml            # un domaine (zone DNS, clés SSH, provider défaut)
│   ├── initech.example/
│   │   ├── loulou.initech.example.yml # un host
│   │   └── mail.initech.example.yml
│   └── initech-fr.example.yml
└── autre-societe/
    └── exemple.com.yml
----

Le *merge* est hiérarchique (plus spécifique gagne) :
`_default.yml` → `<société>/<domaine>.yml` → `<société>/<domaine>/<host>.yml`.

Toutes les commandes qui prennent un host acceptent une *syntaxe path-like* qui
reflète l'arborescence : `initech/loulou.initech.example`, ou `initech/loulou` si le domaine
est sans ambiguïté, ou simplement `loulou` si une seule société est déclarée.

=== Concepts clés

* *Agentless* : rien à installer sur le serveur cible. beryl pilote tout par SSH
  (shard `ssh`, isolation complète de `~/.ssh/config`).
* *Un shard API par fournisseur* — `aloli-crystal/api-ovh`, `aloli-crystal/api-scaleway`,
  `aloli-crystal/api-dedibox`. Chaque shard est autonome, publié MIT, et testé unitairement.
* *Identifiants hétérogènes par provider* : texte `service_name` pour OVH,
  UUID v4 pour Scaleway, entier pour Dedibox. La forme `initech/<ID>` fonctionne
  sur les trois : beryl résout l'IP publique via l'API et enchaîne.
* *Binaire unique Crystal* : `shards build --release` produit `bin/beryl` statique,
  déployable sans runtime sur n'importe quel poste POSIX.

== Fournisseurs supportés

Trois fournisseurs sont pris en charge en avril 2026, par ordre alphabétique.

=== Dedibox (Online.net)

Dedibox identifie les serveurs par un *entier* (ex : `186260`). Les credentials
s'enregistrent via `beryl add-provider initech/dedibox` (API key + secret key
récupérées sur https://console.online.net/).

Le *rescue Dedibox* est une image Debian 12 préparée par l'API. Particularité
critique : le user du rescue n'est *pas* `root` mais `sd-<id>` (ex : `sd-186260`).
Le password est généré par l'API à chaque appel `prepare_rescue`, et la clé SSH
IAM liée au compte est *injectée automatiquement* dans `/home/sd-<id>/.ssh/authorized_keys`
par la plateforme. Beryl orchestre ensuite une promotion vers `root` pour que le
reste du flow (scan, bootstrap, apply) fonctionne comme sur OVH.

Le flow `beryl rescue <host>` affiche quatre étapes numérotées :

* *1/4* — `prepare_rescue(server_id, image=debian-12_amd64)` : récupère le login
  `sd-<id>` et le password temporaire.
* *2/4* — `reboot(server_id, reason="beryl rescue")`. L'API Dedibox retourne
  parfois `false` sur ce POST alors que le hardware reboot bien ; beryl loggue
  un warning et poursuit sur le signal TCP réel.
* *2b/4* — attente de la chute de sshd (preuve que le hardware a lâché).
* *3/4* — attente que `sd-<id>@host` réponde (rescue Debian prêt).
* *4/4* — promote : copie `authorized_keys` dans `/root/.ssh/` et active
  `PermitRootLogin yes` via `sudo -S` (password envoyé sur stdin, jamais
  sur la ligne de commande).

*Limitation connue* : l'API Dedibox/Online ne permet pas de poser le *reverse DNS*
(PTR). `beryl scan --dns` pose bien les records A et AAAA via le fournisseur DNS
déclaré sur le domaine (OVH en pratique) et renomme le serveur côté console si
possible, mais le PTR reste à poser manuellement sur https://console.online.net/
(limitation documentée dans `aloli-crystal/api-dedibox`).

Exemple concret, une commande par bloc pour permettre le copier-coller
individuel :

. Bascule en rescue Debian via l'API Dedibox (4 étapes numérotées).
+
[source,console]
----
beryl rescue initech/186260 --provider=dedibox --apply
----
+
. Scan des disques, pose des records A/AAAA, écriture de `cookie.initech.example.yml`.
+
[source,console]
----
beryl scan initech/186260 --provider=dedibox --dns --apply --hostname=cookie
----
+
. Efface les pools ZFS / partitions résiduels sur les disques déclarés.
+
[source,console]
----
beryl wipe initech/cookie.initech.example --apply
----
+
. Installe FreeBSD 15 via mfsBSD-in-QEMU.
+
[source,console]
----
beryl bootstrap initech/cookie.initech.example --apply
----

=== OVH

OVH identifie un serveur dédié par son `service_name` textuel, généralement de
la forme `ns3156789.ip-51-83-6.eu`. Les credentials s'obtiennent via
`beryl add-provider initech/ovh` : Beryl guide la création d'un token sur
https://eu.api.ovh.com/createToken/ puis appelle `POST /auth/credential` pour
générer une consumer key avec l'ensemble exact des access rules nécessaires.

Le *rescue OVH* est `rescue64-pro`, une image Debian 64 bits. La bascule se fait
en deux temps côté API :

. `dedicated_servers.prepare_rescue(service_name, ssh_key_name)` pose le boot
  order sur rescue et retourne une *task* OVH.
. beryl poll la task jusqu'à son état terminal (`init` → `todo` → `doing` →
  `done`). Un `log_step` vivant affiche le temps passé dans chaque état, ce
  qui permet à l'opérateur de voir immédiatement si une transition bloque.

Une fois la task `done`, Beryl attend le retour SSH sur `root@host`. La clé SSH
à injecter dans le rescue doit être déclarée dans le panel OVH ; son label
(`ssh_key_name`) est ensuite référencé par `ovh.ssh_key_name` dans le YAML
domaine. Si le compte OVH ne contient *qu'une seule* clé, beryl l'auto-sélectionne
et loggue l'information.

Exemple concret, une commande par bloc pour permettre le copier-coller
individuel :

1. Bascule en rescue64-pro via l'API OVH et polling de la task.
+
[source,console]
----
beryl rescue initech/ns3156789.ip-51-83-6.eu --domain=initech.example --apply
----
+
2. Scan des disques, pose A/AAAA + PTR (IPv4/IPv6), rename panel OVH.
+
[source,console]
----
beryl scan initech/ns3156789.ip-51-83-6.eu --domain=initech.example --dns --apply --hostname=cookie
----
+
3. Efface les pools ZFS / partitions résiduels.
+
[source,console]
----
beryl wipe initech/cookie.initech.example --apply
----
+
4. Installe FreeBSD 15.
+
[source,console]
----
beryl bootstrap initech/cookie.initech.example --apply
----
+
5. Dans un second terminal, suit en direct `bsdinstall.log` de la VM mfsBSD.
+
[source,console]
----
beryl follow-install initech/cookie.initech.example
----

Avec `--dns`, `scan` pose A/AAAA vers la zone DNS, PTR via l'API OVH (IPv4 + IPv6)
et renomme le serveur côté panel (le `service_name` reste, mais le *display name*
devient le nom court souhaité).

=== Scaleway

Scaleway Elastic Metal identifie les serveurs par *UUID v4* (ex :
`9783705f-f86f-4bf7-88ad-4c92b920e9ba`), zoné géographiquement (`fr-par-1`,
`fr-par-2`, `pl-waw-3`…). Les credentials s'enregistrent via
`beryl add-provider initech/scaleway` — secret key + project ID, avec la liste
des permissions IAM à cocher manuellement dans la console (pas d'auto-gen
côté API Scaleway).

Le *rescue Scaleway* est un Ubuntu live. Trois spécificités critiques à retenir,
source : https://www.scaleway.com/en/docs/bare-metal/elastic-metal/how-to/use-rescue-mode/ :

. *Le user du rescue est `rescue`*, pas `root`. C'est un sudoer sans mot de
  passe dans l'image rescue officielle.
. *Les clés SSH injectées dans le rescue sont UNIQUEMENT celles de
  `install.ssh_key_ids`*, posées lors de l'install initial du serveur. Ajouter
  une clé au projet Scaleway *après* création du serveur ne propage rien au
  rescue : la clé sera absente de `/home/rescue/.ssh/authorized_keys`.
. *Pour resynchroniser les clés, il faut refaire un install* (opération
  destructrice). beryl expose cette opération via `beryl scaleway-reinstall <host>`,
  qui appelle `POST /servers/{id}/install` avec la liste à jour des clés du
  projet. À n'utiliser que sur un serveur neuf ou dont l'OS peut être perdu.

Pour rendre le flow homogène avec OVH et Dedibox, `beryl rescue` *promeut
automatiquement* `rescue` → `root` après le retour SSH : copie de
`/home/rescue/.ssh/authorized_keys` dans `/root/.ssh/`, activation de
`PermitRootLogin yes` dans `/etc/ssh/sshd_config.d/beryl.conf`, reload de sshd.
Les commandes suivantes (`scan`, `bootstrap`, `apply`) se connectent alors en
`root@host` comme ailleurs.

Avant le reboot Rescue, Beryl effectue un *pre-check* (étape 1/3 dans les logs) :
il lit `install.ssh_key_ids` du serveur, récupère chaque clé publique par son
ID, et compare le base64 avec la clé locale `host.identity_file.pub`. Si la
clé locale n'est pas dans la liste, beryl refuse de procéder et pointe
explicitement vers `beryl scaleway-reinstall`.

Exemple concret (chouquette, zone `pl-waw-3`), une commande par bloc pour
permettre le copier-coller individuel :

1. Pre-check `install.ssh_key_ids` puis bascule en rescue Ubuntu. beryl
   résout l'IP + la zone via l'API à partir de l'UUID et promeut
   `rescue` → `root` après le retour SSH.
+
[source,console]
----
beryl rescue initech/9783705f-f86f-4bf7-88ad-4c92b920e9ba --provider=scaleway --apply
----
+
2. À lancer *uniquement* si le pre-check 1/3 a bloqué : resynchronise les
   clés SSH via l'API officielle. DESTRUCTIF : réinstalle l'OS sur le
   disque. À n'utiliser que sur un serveur neuf.
+
[source,console]
----
beryl scaleway-reinstall initech/9783705f-f86f-4bf7-88ad-4c92b920e9ba
----
+
3. Scan des disques, A/AAAA, reverse DNS IPv4, rename console Scaleway.
+
[source,console]
----
beryl scan initech/9783705f-f86f-4bf7-88ad-4c92b920e9ba --provider=scaleway --dns --apply \
--hostname=chouquette
----
+
4. Efface les pools ZFS / partitions résiduels.
+
[source,console]
----
beryl wipe initech/chouquette.initech.example --apply
----
+
5. Installe FreeBSD 15.
+
[source,console]
----
beryl bootstrap initech/chouquette.initech.example --apply
----

== Installation

1. Clone du dépôt.
+
[source,sh]
----
git clone https://github.com/aloli-crystal/beryl.git
----
+
2. Récupération des dépendances (shards Initech + stdlib).
+
[source,sh]
----
cd beryl && shards install
----
+
3. Build du binaire release.
+
[source,sh]
----
shards build --release
----

Le binaire `beryl` est produit dans `./bin/beryl`. Aucune dépendance runtime
hors `libssl` / `libcrypto` présentes par défaut sur macOS et Linux.

== Démarrage rapide

Chaque commande est en simulation par défaut (elle affiche ce qu'elle ferait) ;
`--apply` l'exécute réellement.

1. Crée l'arborescence `~/.config/beryl/initech/` (prompts interactifs).
+
[source,sh]
----
beryl init initech --apply
----
+
2. Enregistre les credentials OVH dans `~/.config/beryl/.env.yml`.
+
[source,sh]
----
beryl add-provider initech/ovh --apply
----
+
3. Déclare la zone DNS, le fournisseur par défaut, les clés SSH.
+
[source,sh]
----
beryl add-domain initech/initech.example --apply
----
+
4. Bascule le serveur en rescue.
+
[source,sh]
----
beryl rescue initech/cookie.initech.example --apply
----
+
5. Détecte les disques, pose le DNS, écrit le YAML host.
+
[source,sh]
----
beryl scan initech/cookie.initech.example --dns --apply --hostname=cookie
----
+
6. Efface les pools / partitions résiduels.
+
[source,sh]
----
beryl wipe initech/cookie.initech.example --apply
----
+
7. Installe FreeBSD 15.
+
[source,sh]
----
beryl bootstrap initech/cookie.initech.example --apply
----

La référence CLI complète (sous-commandes, shorts, flags) est dans
link:docs/CLI-REFERENCE.adoc[docs/CLI-REFERENCE.adoc]. L'architecture détaillée
et la feuille de route sont dans link:ARCHITECTURE.adoc[ARCHITECTURE.adoc] et

== Migrer PostgreSQL vers une version majeure

`beryl pg-upgrade <host>` migre le serveur PostgreSQL d'un hôte FreeBSD vers
une nouvelle version majeure (ex. 18 → 19) avec `pg_upgrade`, selon la
procédure du fichier `UPDATING` des ports FreeBSD. Simulation par défaut :
beryl détecte les versions, les data dirs et les options du cluster, vérifie
les préconditions et affiche le plan.

[source,sh]
----
beryl pg-upgrade acme/db1.example.net --to 19 --stop-services monappli
beryl pg-upgrade acme/db1.example.net --to 19 --stop-services monappli --apply
----

Ce que beryl vérifie avant tout geste :

* le paquet `postgresqlNN-server` cible est au dépôt (`--to`, sinon la
  version la plus récente du dépôt) ;
* les paquets installés qui dépendent de PostgreSQL (pilotes, extensions)
  existent au dépôt reconstruits pour la nouvelle version. Sinon, beryl
  refuse : reconstruisez d'abord le dépôt avec `DEFAULT_VERSIONS+= pgsql=NN` ;
* l'espace disque (copie du data dir + sauvegarde `pg_dumpall`).

Le nouveau cluster reprend l'encodage, la locale et l'état des data
checksums de l'ancien. `pg_upgrade --check` passe en premier. En cas d'échec
avant le démarrage du nouveau serveur, beryl revient automatiquement à
l'ancienne version. `--link` est plus rapide mais interdit tout retour arrière
une fois le nouveau serveur démarré.

L'ancien data dir est conservé. Une fois la nouvelle version validée :

[source,sh]
----
beryl pg-upgrade acme/db1.example.net --cleanup --apply
----

== Niveaux RAID (ZFS)

`beryl scan` demande le niveau RAID de chaque pool sous forme d'un numéro.
Les numéros 5, 6 et 7 sont une convention de beryl, par analogie avec les
RAID matériels ; ZFS, lui, parle de `raidz`, `raidz2` et `raidz3`. Seuls les
niveaux réalisables avec les disques choisis sont proposés.

[options="header",cols="1,2,5,1,1,2"]
|===
| Choix | Mode ZFS | En clair | Disques min. | Pannes tolérées | Capacité utile (N disques)

| `0` | stripe | Données *réparties* sur tous les disques, sans copie. Le plus rapide et le plus d'espace, mais un disque perdu = tout perdu. | 1 | 0 | N
| `1` | mirror | *Miroir* : chaque disque porte la même copie. | 2 | N − 1 | 1 disque
| `5` | raidz | Parité *simple* (équivalent RAID 5). | 3 | 1 | N − 1
| `6` | raidz2 | Parité *double* (équivalent RAID 6). | 4 | 2 | N − 2
| `7` | raidz3 | Parité *triple* (propre à ZFS). | 5 | 3 | N − 3
| `10` | mirror_stripe | *Miroirs par paires*, données réparties sur les paires (RAID 10). | 4, nombre pair | 1 par paire | N / 2
|===

Repères :

* *2 disques* : `1` (miroir) est le seul choix redondant.
* *3 disques* : `5` (raidz).
* *4 disques et plus* : `6` (raidz2) pour la sécurité et l'espace — il
  supporte deux pannes simultanées, précieux avec de gros disques dont la
  reconstruction dure des heures ; `10` pour la performance (bases de
  données), au prix de la moitié de l'espace.
* `0` ne convient qu'à des données jetables (cache) ou si l'on s'en remet
  entièrement aux sauvegardes. Pour un zroot de plusieurs disques en `0`,
  `beryl scan` avertit et demande confirmation.
