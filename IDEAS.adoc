== Groupes de serveurs

=== Idée

Permettre de regrouper les hôtes de l'inventaire par *groupe*, où chaque
groupe partage la même installation : mêmes recettes appliquées, mêmes
variables de base, possiblement même hébergeur. Un hôte est alors
*installé à la façon de son groupe*.

=== Pourquoi

À 50 serveurs, la plupart ne sont pas uniques : on a typiquement des
rôles récurrents (`web-front`, `db-primary`, `worker`, `proxy`, etc.).
Recopier la même liste de recettes sur chaque hôte crée de la redondance
et dérive facilement (on oublie de mettre à jour un hôte sur dix).

Le groupe comme *unité d'installation* simplifie aussi le diff mental :
« ce qui change entre deux hôtes du même groupe doit être une exception
documentée, pas un oubli ».

=== Esquisse YAML

[source,yaml]
----
# Sections de groupe déclarées au niveau racine de inventory.yml.
groups:
  web-front:
    provider: ovh
    recipes:
      - core-system
      - nginx-deploy
      - sshd-hardening
    variables:
      timezone: Europe/Paris
      nginx_profile: mozilla-modern

  db-primary:
    provider: ovh
    recipes:
      - core-system
      - postgresql-primary
    variables:
      postgres_version: "17"
      data_on_home: true

hosts:
  web01.aloli.fr:
    group: web-front

  web02.aloli.fr:
    group: web-front
    port: 2222 # override ponctuel, reste dans web-front

  db01.aloli.fr:
    group: db-primary
----

=== Questions ouvertes à trancher

* *Héritage et override.* Priorité de résolution `host > group > defaults`,
  comme pour les champs actuels (`user`, `port`, etc.) ? C'est le plus
  cohérent avec l'existant.
* *Multi-groupes.* Un hôte peut-il appartenir à *plusieurs* groupes
  (`group: [web-front, monitoring-client]`) ? Utile pour composer des
  rôles mais complique la résolution des conflits.
* *Héritage entre groupes.* Un groupe `all` comme base implicite,
  puis `web-front` qui en étend les recettes ? Ou interdire l'héritage
  entre groupes pour rester simple ?
* *Impact CLI.*
** `beryl apply web01.aloli.fr` : applique les recettes effectives
   (groupe + overrides).
** `beryl apply --group web-front` : applique sur tous les hôtes du
   groupe en parallèle.
** `beryl list-hosts --group web-front` : filtre par groupe.
* *Variables fusionnées vs scalaires.* Si le groupe a
  `variables.nginx_upstreams: [a, b]` et l'hôte définit
  `variables.nginx_upstreams: [c]`, est-ce override (remplacement) ou
  fusion ? Probablement override, avec une syntaxe `!merge` ou `+=` si
  fusion explicite souhaitée. Trancher.
* *Validation.* Refuser un inventaire qui référence un groupe inexistant
  (`group: web-fornt` typo) pour éviter un silencieux « aucune recette ».

=== Impact sur les structures Crystal existantes

Dans l'état actuel de `Beryl::Inventory` :

* `Host` récupère aujourd'hui ses recettes directement depuis sa section
  YAML. Il faudra introduire une résolution à deux étages : lookup du
  groupe, fusion avec les overrides de l'hôte.
* Ajouter une classe `Group` symétrique de `Host` (provider, recipes,
  variables).
* Méthode `Inventory#resolve(host_name)` qui renvoie un `Host` effectif
  avec toutes les variables/recettes résolues (sans mutation de
  l'original).

== Cible d'installation multi-OS (pas uniquement FreeBSD)

=== Idée

L'installation actuelle est verrouillée sur FreeBSD 15 en pkgbase (ADR-001).
À terme, beryl doit pouvoir provisionner *d'autres systèmes d'exploitation*
avec la même mécanique (rescue → bascule → installation → configuration).

Cibles envisageables :

* *Linux* : Debian, Ubuntu, Alpine, Rocky/AlmaLinux, NixOS.
* *BSD* : OpenBSD, NetBSD en plus de FreeBSD.
* *Illumos* : OmniOS, SmartOS pour les amateurs.

=== Pourquoi

* Les 50 serveurs cibles actuels sont tous FreeBSD, mais l'écosystème
  beryl (architecture agentless SSH, recettes YAML, conventions Mozilla
  Modern) est par nature générique.
* Beaucoup d'opérateurs voudront un seul outil pour leur parc hétérogène.
* Reste pertinent face à Chef/Puppet/Ansible qui gèrent tous plusieurs OS.

=== Esquisse

Dans l'inventaire, chaque groupe (ou hôte) déclare son *target_os* :

[source,yaml]
----
groups:
  web-front:
    target_os: freebsd-15
    recipes: [core-system, nginx-deploy]

  worker-linux:
    target_os: debian-13
    recipes: [core-system, nginx, docker]

  edge:
    target_os: openbsd-7.6
    recipes: [core-system, pf-firewall]
----

Chaque `target_os` implique :

* Une *stratégie de bootstrap* dédiée (mfsBSD pour FreeBSD, debootstrap
  ou ISO live pour Debian, ramdisk OpenBSD, etc.).
* Un *installeur* spécifique (pkgbase pour FreeBSD, debootstrap + chroot
  pour Debian, auto_install pour OpenBSD, etc.).
* Un *catalogue de ressources* adapté (`pkg` FreeBSD vs `apt` Debian vs
  `pkg_add` OpenBSD).

=== Questions ouvertes à trancher

* *Architecture du code.* Interface `Bootstrapper` et `Installer`
  abstraite, implémentations concrètes par OS. Un dossier `bootstrap/`
  contiendrait `freebsd/`, `debian/`, `openbsd/`, etc.
* *Abstraction des ressources.* Une ressource `pkg` cross-OS qui délègue
  à `pkg`/`apt`/`pkg_add` selon le `target_os` ? Ou des ressources
  distinctes `pkg_freebsd`, `pkg_debian`, etc. ? Pencher vers la
  première (abstraction) pour que les recettes restent portables.
* *Gestion des différences fondamentales.* FreeBSD a ZFS natif, rc.d,
  jails ; Debian a systemd, LVM, containers ; OpenBSD a rcctl, pf.
  Comment exprimer ces différences dans les recettes ? Variantes de
  recettes par OS ? Blocs conditionnels `when_os:` ?
* *Bootstrap mfsBSD réutilisable.* Voir la section suivante
  « Génération d'ISO préprovisionnées ».
* *Priorité.* Tant que FreeBSD n'est pas *complètement* éprouvé (Phase 2
  terminée, 50 serveurs en production), ne pas disperser l'effort sur
  d'autres OS. Ouvrir le chantier multi-OS après v1.0 stable.

=== Impact sur les ADR existants

ADR-001 (FreeBSD 15 en pkgbase) deviendrait : « OS par défaut : FreeBSD 15,
avec architecture ouverte pour d'autres cibles via `target_os:` ». À
re-documenter le moment venu, en parallèle d'un nouvel ADR décrivant
l'architecture de l'abstraction multi-OS.

== Génération d'ISO préprovisionnées

=== Idée

Produire une ISO *self-contained* qui, une fois bootée, a déjà la clé SSH
dans `/root/.ssh/authorized_keys` et sshd démarré. Plus rien à taper
dans la fenêtre QEMU ni dans la console KVM distante — on boote, on se
connecte en SSH, c'est prêt.

C'est le même pattern que `depenguin.me` applique à mfsBSD : partir
d'une ISO officielle, y injecter les clés de l'opérateur, servir l'ISO
custom. beryl ferait de même pour Linux (et éventuellement reprendrait
ce mécanisme pour mfsBSD afin de fermer la boucle du bootstrap).

=== Deux voies techniques

==== (A) Seed cloud-init

Laisse l'ISO principale intacte. Génère à côté une *toute petite* ISO
(~5 Ko) qui contient :

* `meta-data` : identifiants de l'instance
* `user-data` : configuration cloud-init (installer openssh, injecter la clé)

QEMU attache les *deux* ISO en cdrom. Cloud-init, présent par défaut
dans Ubuntu Server live et les images cloud Debian, lit automatiquement
la seconde ISO au boot et applique la configuration.

*Avantages* : simple, outil nécessaire minime (`xorriso` ou
`cloud-localds`), ISO principale inchangée (mises à jour Debian faciles).

*Limite* : nécessite un OS cible avec cloud-init actif. Les ISO Debian
live « standard » ne l'ont pas toujours.

==== (B) ISO remastérisée

Modifie l'ISO principale elle-même : extraction, modification du
squashfs/initrd pour y ajouter la clé et un script de démarrage sshd,
recompilation.

*Avantages* : fonctionne même sans cloud-init. Résultat : une seule
ISO, bootable telle quelle partout (même un rescue distant où on
uploade un fichier unique).

*Inconvénients* : chaîne d'outils plus lourde (`xorriso`,
`squashfs-tools`, parfois `mkinitramfs`). Rebuild de quelques minutes
à chaque nouvelle clé ou changement de script.

=== Piste à privilégier

Pour démarrer : *voie (A)* avec Ubuntu Server live (déjà cloud-init).
Nouvelle sous-commande :

[source,sh]
----
beryl bake-seed --pubkey ~/.ssh/id_ed25519.pub --output ~/vms/seed.iso
----

Extension de `launch.sh` : si le YAML VM contient un champ `seed_iso:`,
QEMU attache un second cdrom.

La voie (B) reste pertinente pour produire un « beryl-rescue-debian.iso »
utilisable *sans* cloud-init (typiquement un rescue bas niveau), mais
son coût d'implémentation (unsquashfs/resquashfs + tests) est bien
supérieur. À instruire quand la voie (A) montrera ses limites.

=== Cas d'usage

* *Local UTM/QEMU* : `bake-seed` + attache du seed.iso → VM prête sans
  `prep-rescue`.
* *Rescue hébergeur* : si l'hébergeur autorise l'upload d'une ISO custom
  (Hetzner oui, OVH plutôt non), l'ISO remastérisée (B) devient utile.
  Sinon `prep-rescue` reste pertinent.
* *mfsBSD* : le même outillage de remastering s'applique à mfsBSD avant
  le `dd` — exactement ce que fait depenguin.me.

== Bootstrap UEFI-compatible — pivot post-ADR-010

=== Contexte

link:ARCHITECTURE.adoc[ADR-010] a invalidé le flux « dd mfsBSD ISO +
reboot » sur les dédiés UEFI-only (cas majoritaire OVH/Scaleway/Hetzner
en 2026). Cette section compare les deux pistes viables pour le pivot
de l'architecture `Beryl::Bootstrap::*`.

=== Piste A — QEMU-in-rescue (pattern depenguin.me)

*Principe.* Ne pas booter mfsBSD sur le métal. L'exécuter en machine
virtuelle *depuis le rescue Linux*, avec le disque physique en
passthrough. Lancer `bsdinstall` à l'intérieur du QEMU qui écrit un
FreeBSD nativement UEFI-bootable sur le disque. À l'arrêt du QEMU,
rebooter le métal : UEFI trouve une ESP + `loader.efi` FreeBSD normal.

*Flux beryl.*

. `apt install -y qemu-system-x86 ovmf` dans le rescue Linux (ou
  equivalent de la distro).
. Téléchargement mfsBSD ISO + vérification empreinte.
. Lancement QEMU : `-machine q35 -bios OVMF.fd -drive file=/dev/nvme0n1,format=raw,if=virtio -cdrom mfsbsd.iso -netdev user,hostfwd=tcp::2222-:22`.
. Attente SSH dans le QEMU (ligne de vie via user-mode networking).
. Upload + exécution de notre `installerconfig` / `install-pkgbase.sh`
  à l'intérieur du QEMU.
. bsdinstall écrit FreeBSD sur le disque réel (vu comme `/dev/vda`
  dans le QEMU).
. Shutdown QEMU propre (poweroff depuis la VM).
. `reboot -f` du métal.
. Attente SSH sur le FreeBSD fraîchement posé.

*Avantages.*

* Pattern éprouvé (depenguin.me tourne ainsi depuis 2022).
* QEMU fournit son propre firmware (OVMF) donc UEFI en VM,
  indépendant du firmware bare metal.
* `bsdinstall` fait le travail standard FreeBSD : partitionnement
  UEFI-compatible, `loader.efi`, rc.conf, etc.

*Inconvénients.*

* Couche QEMU lourde : ~50 Mo d'install dans le rescue, RAM partagée
  entre rescue Linux et VM mfsBSD (4 Go minimum conseillé).
* Dépendances hôte : `qemu-system-x86`, `ovmf`. Certains rescues
  minimaux (notamment Hetzner netboot) n'ont pas `apt` fonctionnel par
  défaut — il faut prévoir un fallback.
* Orchestration à deux étages : beryl côté poste local pilote le rescue
  Linux, qui pilote mfsBSD dans QEMU. Trois cercles de SSH à gérer,
  avec un changement de clé d'hôte entre mfsBSD et FreeBSD final.
* Temps d'install plus long : lancement QEMU + boot mfsBSD dans la VM
  (~1 min) avant bsdinstall.

=== Piste B — FreeBSD memstick hybride + `installerconfig` embarqué

*Principe.* Utiliser l'image officielle
`FreeBSD-15.0-RELEASE-amd64-memstick.img`, qui est une **image disque
hybride** (MBR + GPT + ESP + UFS + installateur) déjà UEFI-bootable
nativement. Remasteriser l'image côté rescue pour y injecter un
`/etc/installerconfig` qui scripte l'install (pkgbase, hostname, clé
SSH root). `dd` l'image remasterisée sur le disque, reboot : UEFI
amorce directement FreeBSD-installer, qui lit installerconfig, fait
l'install non interactive, puis reboote sur FreeBSD final.

*Flux beryl.*

. Téléchargement memstick officiel + vérification empreinte.
. Montage en loopback de l'image (read-only UFS, Linux le lit avec
  `ufstype=ufs2`).
. Copie du contenu vers un working dir dans le rescue.
. Ajout de `/etc/installerconfig` généré par beryl (partitionnement
  ZFS, liste de paquets pkgbase, hostname, authorized_keys root).
. Regénération d'une image UFS avec `makefs -t ffs` (provient de
  `freebsd-buildutils` ou compilé depuis `src/usr.sbin/makefs` de
  FreeBSD).
. Reconstruction des entêtes GPT + ESP autour du nouveau UFS (peut
  se faire en Crystal pur via `aloli-crystal/silex` étendu ou à la main
  avec `sgdisk` + `mkfs.vfat`).
. `dd` sur le disque, `reboot -f`.
. Attente SSH sur le FreeBSD installé.

*Avantages.*

* Une seule image, un seul boot : pas de couche QEMU, pas de double
  passage rescue → mfsBSD → FreeBSD.
* Architecture beryl simplifiée : `Bootstrap::MfsBSD` et
  `Bootstrap::Installer` fusionnent en un `Bootstrap::Memstick`.
* Image officielle FreeBSD, signée, distribuée sur tous les miroirs.
  Pas de dépendance à un projet tiers (depenguin.me).

*Inconvénients.*

* **Remastering UFS depuis Linux non trivial.** Le kernel Linux lit
  UFS mais écrit difficilement (support en lecture stable, écriture
  expérimentale). Il faut passer par `makefs` qui est un binaire BSD —
  cross-compilable pour Linux mais pas packagé dans Debian/Ubuntu.
  Alternatives :
** Fournir un binaire `makefs` statique pré-compilé dans un futur
   shard `crystal-ufs-tools` (autonomie mais maintien du binaire).
** Utiliser `mtools` + un contournement : `mtools` sait manipuler
   FAT uniquement. Pas applicable.
** Extraire les fichiers de l'image, modifier, et `dd` l'image intacte
   puis écraser le fichier `installerconfig` à l'offset où il se
   trouve dans l'image. Hack ingénieux mais fragile (UFS avec
   journaling peut déplacer les blocs).
* Dépendance à `installerconfig` : bien documenté mais rare à
  automatiser en dehors des environnements cloud/Vagrant.

=== Questions ouvertes à trancher lors de la refonte

* Quelle piste valider en premier ? Plutôt *A* (plus rapide à
  prototyper, pattern éprouvé) avant de tenter *B* (plus élégant à
  long terme mais remastering UFS à résoudre).
* Peut-on faire un **fallback BIOS Legacy** pour les quelques serveurs
  encore en mode Legacy (ancien Kimsufi, VM QEMU locales) ? Oui, l'ADR
  actuel marche encore pour ces cas — conserver le code existant en
  chemin secondaire activable via `--legacy-bios`.
* Est-ce qu'on **pousse** la piste A vers un shard dédié
  `crystal-qemu-orchestrator` si le patron se réutilise ailleurs
  (tests locaux, CI FreeBSD custom, etc.) ?
* Pour la piste B, y a-t-il une **piste C** (serveur HTTP beryl qui
  sert l'installerconfig, boot loader FreeBSD configuré pour
  fetch) qui éviterait le remastering UFS ? À creuser — le loader
  FreeBSD a des variables `installerconfig_url` théoriquement
  fetchables.

=== Recommandation immédiate

Piste **A (QEMU-in-rescue)** pour le premier pivot, parce que :

. Elle repose sur un pattern validé en production depuis 3+ ans (depenguin.me).
. Elle peut être prototypée manuellement dans le rescue lors du prochain
  test — on valide le concept avant de l'automatiser dans beryl.
. Les dépendances (`qemu-system-x86`, `ovmf`) sont dans les dépôts
  standards Debian/Ubuntu/Alma — `apt install` suffit dans la majorité
  des rescues.

Piste **B** reste la cible long terme pour simplifier l'architecture
quand le remastering UFS sera outillé proprement (shard Crystal ou
binaire statique embarqué dans beryl, cf. principe d'autonomie).

== Séparation des utilisateurs système : `admin` vs `deploy`

=== Principe

Rupture volontaire avec la convention historique du gist v2ror
(où `deploy` était dans `wheel`). Dans beryl, les rôles se séparent :

[cols="1,2,2"]
|===
| User | Groupe primaire + groupes secondaires | Rôle

| `admin`
| `staff` + `wheel`
| Humain. Shell `csh` (tradition BSD). Maintenance système, sudo,
  installation dans `/opt`, upgrades.

| `deploy`
| `www` (**pas** `wheel`)
| Fonctionnel. Shell `sh`. Exécute les applis Marten/Kemal/Rails,
  aucun sudo, aucun droit système.
|===

=== Installation Ruby via ruby-install + chruby (pattern FreeBSD-idiomatique)

*Outils* (tous installés en pkg, pas de compilation manuelle) :

* `pkg install sudo` : non présent dans la base FreeBSD, à installer
  explicitement.
* `pkg install ruby-install` : installateur de Rubies upstream (support
  MRI, jruby, truffle, etc.).
* `pkg install chruby` : bascule de version via `~/.ruby-version` +
  shim `auto.sh` qui déclenche le switch sur `cd`.
* `pkg install zsh` : shell par défaut de `deploy`, complété par
  oh-my-zsh installé au niveau utilisateur.

*Chemins résultants* :

[source,sh]
----
/usr/local/share/rubies/ruby-3.3.0/    # ruby-install système (sudo)
/usr/local/share/rubies/ruby-3.4.0/    # versions multiples cohabitent
----

`chruby` détecte automatiquement `/usr/local/share/rubies/*` et le
`~/.rubies/*` de chaque user.

*Passenger + nginx* (même logique `/opt` mais tourne sur la Ruby
choisie par chruby pendant la compilation) :

[source,sh]
----
/opt/ruby-3.3.0-passenger-6.0.20/      # build Passenger pour Ruby 3.3
/opt/nginx → ruby-3.3.0-passenger-6.0.20/   # actif
----

*Responsabilités* :

* *`admin`* + `sudo` : installe les pkgs, lance `sudo ruby-install ...`,
  compile Passenger, maintient les symlinks `/opt/nginx`.
* *`deploy`* : ne touche pas aux versions. Son `~/.zshenv` source
  chruby et sélectionne via `~/.ruby-version` dans les dossiers d'app.

*Exemple de `.zshenv` de référence* (depuis la production v2ror) :

[source,sh]
----
source /usr/local/share/chruby/chruby.sh
source /usr/local/share/chruby/auto.sh
chruby `cat ~/.ruby-version`
export LANG=fr_FR.UTF-8
export LC_ALL=fr_FR.UTF-8
umask 0002
----

Bascule entre versions : modifier `~/.ruby-version` de l'app et
`cd`-re-dans le dossier → chruby re-sélectionne la bonne Ruby,
aucune commande admin requise.

=== Pourquoi

* *Moindre privilège* : `deploy` compromis → aucune escalade root possible.
* *Partage* : d'autres utilisateurs système (monitoring, backup, etc.)
  peuvent invoquer `/opt/ruby/bin/ruby` sans friction.
* *Versions multiples cohabitantes* : zéro modif utilisateur, juste des symlinks.
* *Réversibilité* : `ln -sfn` atomique permet un rollback trivial.

=== Impact sur `Beryl::Bootstrap::QemuInRescue`

L'`installerconfig` généré par beryl doit créer **les deux utilisateurs
dès l'install** avec la clé SSH de l'opérateur :

[source,sh]
----
pw useradd admin  -g staff -G wheel -s /bin/csh -m
pw useradd deploy -g www              -s /bin/sh  -m
# Pose la clé SSH dans les deux homes
----

Côté sshd, le défaut FreeBSD `PermitRootLogin no` est **conservé**.
Connexions administratives : `ssh admin@host && sudo -i`.
Connexions applicatives (deploy) : `ssh deploy@host`.

== Multi-disque et RAID : `beryl list-disks` + `DiskLayout`

=== Contexte

Le bootstrap v1 (ADR-011, single-disk) couvre le cas minimaliste des
Kimsufi 1 disque. Dès qu'un serveur a plusieurs disques (2 SSD mirror,
2×NVMe + 4×HDD, etc.), il faut enrichir l'architecture.

Deux cas d'usage concrets identifiés :

* Serveur **aito** (OVH) — 2×512 Go NVMe, RAID 0. Équivalent ZFS :
  boot pool `zroot` en `stripe` sur les deux NVMe (2× capacité, 0
  redondance — assumée par le choix de l'opérateur).
* Serveur de test **4×6 To HDD SATA + 1×500 Go NVMe**. Layout idiomatique :
  ** *boot pool* `zroot` sur NVMe seul (petit, réinstallable en cas de perte)
  ** *data pool* `ztank` sur les 4 HDD en `raidz2` (tolérance 2 pannes)

=== `beryl list-disks <host>`

Sous-commande à ajouter. Rôle : inspecter le rescue, présenter l'état
brut + une suggestion.

*Sortie type* :

----
Host: loulou.aloli.net (rescue OVH Debian 12)

SSD/NVMe :
  nvme0n1   INTEL SSDPE2KE016T8   500 Go    rota=0

HDD :
  sda       WDC WD60EFAX-68SHWN0  6000 Go   rota=1
  sdb       WDC WD60EFAX-68SHWN0  6000 Go   rota=1
  sdc       WDC WD60EFAX-68SHWN0  6000 Go   rota=1
  sdd       WDC WD60EFAX-68SHWN0  6000 Go   rota=1

Suggestion beryl :
  boot_pool: nvme0n1 (stripe)
  data_pool: sda/sdb/sdc/sdd (raidz2, ~12 To usables, 2 pannes tolérées)
----

*Implémentation* : parse `lsblk -Jdno NAME,SIZE,ROTA,MODEL,TYPE` (JSON
pour robustesse), regroupe par type, génère une suggestion heuristique.

=== `DiskLayout` — structure passée à `QemuInRescue`

[source,crystal]
----
struct DiskLayout
  struct Pool
    getter name : String
    getter disks : Array(String)
    getter topology : Topology # :stripe | :mirror | :raidz1 | :raidz2 | :raidz3
  end

  getter boot : Pool                 # celui que bsdinstall installe
  getter data : Array(Pool)          # pools supplémentaires créés en post-install
end
----

*bsdinstall* gère nativement `ZFSBOOT_VDEV_TYPE` (stripe/mirror/raidz*)
et `ZFSBOOT_DISKS` pour le pool de boot. Les pools data sont créés en
post-install via `zpool create ztank raidz2 ada0 ada1 ada2 ada3`.

=== Inventaire YAML (déclaratif, recommandé)

[source,yaml]
----
hosts:
  big-db-01.aloli.fr:
    provider: ovh
    install:
      disk_layout:
        boot:
          name: zroot
          disks: [nvme0n1]
          topology: stripe
        data:
          - name: tank
            disks: [sda, sdb, sdc, sdd]
            topology: raidz2
----

*Note* : les noms des disques sont ceux vus *depuis la VM QEMU*
(`vtbd0`, `vtbd1`…) *ou* ceux du bare metal ; beryl doit traduire
automatiquement — en passant les disques réels à QEMU via `-drive`,
l'ordre détermine le nom en VM (`vtbd0` = premier `-drive`, etc.).

=== Questions ouvertes

* Faut-il *chiffrer* le data pool par défaut (ZFS native encryption) ?
  Probablement non — overhead perf, gestion clés, contexte serveur
  dédié physiquement contrôlé.
* Que faire si le rescue voit un disque qui n'est *pas* cité dans le
  layout YAML ? Erreur stricte ? Warning ? Ne rien faire ?
  Pencher vers erreur stricte pour éviter les mauvaises surprises
  (oublier un disque = data perdue en silence).
* Comment gérer les upgrades (ajouter un disque à un pool raidz
  existant) ? Pas dans bootstrap, mais recette Phase 2 dédiée.

== Provisioning via API hébergeur (OVH, Scaleway)

=== Idée

Piloter le cycle de vie *complet* d'un serveur via les APIs OVH et
Scaleway : commander, installer, nommer, configurer DNS direct + reverse
DNS, enregistrer dans l'inventaire beryl — **sans jamais toucher au panel
web**. L'opérateur déclare ce qu'il veut dans un YAML, beryl fait tout le
reste.

Objectif : zéro interaction, zéro erreur humaine, déploiement de 10 ou
50 serveurs en parallèle.

=== Portée fonctionnelle

. *Acheter* un serveur dédié via l'API.
  ** OVH : `/order/cart` (plus complexe, workflow panier + validation).
  ** Scaleway : `POST /baremetal/v1/zones/{zone}/servers` (order + install
     en un appel).
. *Attribuer un nom* — soit passé par l'opérateur, soit suggéré par
  beryl selon une convention (`<role>-<index>-<région>`, ex. `web-01-gra`).
. *Enregistrer en DNS* (A/AAAA) via l'API du registrar (deploy
  le fait déjà pour OVH et Gandi).
. *Configurer le reverse DNS* IPv4 et IPv6 :
  ** OVH : `POST /ip/{ip}/reverse` pour chaque IP (v4 + v6).
  ** Scaleway : champ `reverse` dans la config du serveur bare metal.
. *Installer Debian* (ou Ubuntu) via l'API avec la clé SSH du compte.
. *Attendre la fin de l'install* en polling sur le `taskId` (OVH) ou les
  `events` (Scaleway).
. *Enregistrer l'hôte dans `inventory.yml`* (update automatique).
. *Enchaîner `beryl bootstrap`* → mfsBSD → FreeBSD.

Tout en idempotent : rejouer la commande sur un serveur déjà provisionné
ne recrée rien, elle vérifie et passe.

=== Exemple d'utilisation cible

[source,sh]
----
beryl provision \
  --provider ovh \
  --template kimsufi-ks-a \
  --role web \
  --region gra \
  --dns-zone aloli.fr \
  --ssh-key-id papilip
----

Ou via un fichier déclaratif `orders.yml` :

[source,yaml]
----
orders:
  - provider: ovh
    template: kimsufi-ks-a
    count: 3
    role: web
    region: gra
    dns_zone: aloli.fr

  - provider: scaleway
    template: EM-A115X-SSD
    count: 2
    role: db
    zone: fr-par-2
    dns_zone: aloli.fr
----

`beryl provision --orders orders.yml` → 5 serveurs achetés, installés,
en DNS, avec reverse DNS, prêts pour `beryl bootstrap`.

=== Architecture technique

Deux shards **crystal-ovh-api** et **crystal-scw-api** (organisation
`aloli-crystal`), réutilisables pour d'autres projets Aloli (deploy
par exemple).

Périmètre minimal de chaque shard :

* Auth signée (OVH : consumer key + app key/secret) ou bearer (Scaleway).
* Client HTTP Crystal pur (pas de wrapper lourd).
* Modèles des entités utilisées : `Server`, `Task`, `SshKey`, `Install`,
  `ReverseDns`.
* Gestion des erreurs typées (`RateLimited`, `Unauthorized`,
  `NotFound`, etc.).

Dans beryl :

----
src/beryl/
├── providers/
│   ├── provider.cr     # interface abstraite commune
│   ├── ovh.cr          # instancie crystal-ovh-api
│   └── scaleway.cr     # instancie crystal-scw-api
└── cli/
    └── provision.cr    # sous-commande `beryl provision`
----

=== Gestion des secrets

Variables d'environnement ou fichier local `~/.config/beryl/credentials.yml`
*non versionné*. beryl les lit à la demande, ne les stocke pas en clair
dans l'inventaire.

Exemple de `credentials.yml` :

[source,yaml]
----
ovh:
  application_key:    XXXXX
  application_secret: XXXXX
  consumer_key:       XXXXX
  endpoint:           ovh-eu

scaleway:
  secret_key:     XXXXX
  default_zone:   fr-par-2
  default_project_id: XXXXX
----

=== Questions ouvertes à trancher

* *Commander par API OVH* : workflow `/order/cart` est complexe et
  implique validation manuelle (paiement). Jusqu'où pousse-t-on
  l'automatisation ? Probablement : beryl prépare le cart, demande
  confirmation, l'utilisateur clique. Ensuite beryl prend la main sur
  le serveur livré.
* *Validation des ressources avant achat* : vérifier la disponibilité,
  le prix, le datacenter — avant de finaliser l'order. Éviter qu'un
  script se fasse commander accidentellement 50 serveurs à 500 €/mois.
* *Suggestion de noms* : convention par défaut à proposer
  (`<role>-<NN>-<dc>`), avec vérification d'unicité dans l'inventaire
  et dans le DNS.
* *Reverse DNS sur `/ip`* : OVH gère le reverse par IP individuelle ;
  pour un /64 IPv6 entier c'est impraticable, il faut cibler l'IP
  principale du serveur.
* *Inventaire auto-rempli* : après provisioning, comment merger la
  nouvelle entrée dans un `inventory.yml` existant tout en préservant
  les commentaires / customisations de l'opérateur ? Piste : écrire
  dans un fichier séparé `inventory.d/provisioned.yml` qu'on `include`.

=== Impact sur les ADR

Ajoutera un nouvel ADR (post-v1) décrivant :

* L'architecture provider-agnostic (interface `Beryl::Providers::Provider`).
* La convention de gestion des secrets.
* La politique de validation avant achat (confirmations interactives).
* L'intégration avec l'idée « Groupes de serveurs » (un ordre produit
  plusieurs membres d'un groupe).

== Headscale comme couche réseau privée

=== Idée

Utiliser https://github.com/juanfont/headscale[Headscale] (control
plane open-source pour Tailscale, basé sur WireGuard) comme *couche
réseau privée* entre les serveurs gérés par beryl, le poste
opérateur, et les services internes Aloli (Tang, monitoring,
backup, etc.). Tous les hôtes participent à un mesh WireGuard
authentifié, joignables via leurs IPs Tailscale (`100.64.0.0/10`)
sans exposer SSH ni Tang sur l'internet public.

=== Pourquoi

* *Réduction de la surface d'attaque* : SSH et Tang ne sont plus
  accessibles depuis l'internet, seulement via le mesh. Un attaquant
  qui n'est pas dans le mesh ne peut pas tenter de bruteforce SSH
  ni interroger Tang.
* *Cohérence avec le modèle de chiffrement* (Option D Tang) : la
  promesse « si le serveur sort du réseau de confiance, Tang devient
  inaccessible et les données sont illisibles » est *cryptographiquement
  garantie* — la clé Tang ne peut être négociée qu'en étant dans le
  mesh WireGuard.
* *Self-hosted, conforme philosophie Aloli* : Headscale tourne sur
  un VPS / NAS interne Aloli, pas de dépendance au SaaS Tailscale.
  WireGuard est standard moderne audité.
* *Performance* : WireGuard a un overhead négligeable, kernel
  module FreeBSD (`if_wg`) disponible nativement depuis FreeBSD 13.
* *Facilité d'usage* : `tailscale up` côté client = inscription en
  une commande. Côté beryl, le bootstrap pose la pre-auth-key et le
  serveur joint le mesh tout seul au premier boot.

=== Cas d'usage spécifiques pour beryl

==== 1. Tang accessible uniquement via Headscale

Plutôt qu'exposer Tang sur une IP publique avec ACL stricte (compromis
fragile), Tang écoute sur l'IP Tailscale du host Aloli :

[source]
----
Tang URL côté beryl :  http://100.64.0.10:8888/
                                ↑ IP Tailscale du host tang-1.aloli.headscale
----

Au boot d'un serveur encrypted :
. Le serveur monte son lien WireGuard via `tailscale up --auth-key=...`
  (clé pré-posée par bootstrap, expirable).
. `crystal-clevis-zfs unlock` interroge `http://100.64.0.10:8888`.
. Le mesh route vers le Tang. Réponse OK → unlock.

Si le serveur est volé et sorti du mesh : le `tailscale up` échoue
(la pre-auth-key ne suffit pas si le control plane Headscale ne
reconnaît plus la machine, contrôle d'authent côté serveur). Tang
devient inaccessible. Données illisibles. Promesse défendue.

==== 2. `beryl <commande> <host>` via le mesh

`host.ssh_host` du YAML peut pointer vers l'IP Tailscale (genre
`100.64.0.42` ou un nom DNS interne `quantas.aloli.headscale`)
plutôt que l'IP publique. Le fix `ssh_host` du 28 avril 2026 (cf.
`feedback_no_bug_workaround.md`) garantit que beryl respecte
l'override YAML.

[source,yaml]
----
freebsd:
  hostname: quantas
  ssh_host: 100.64.0.42         # IP Tailscale stable
provider: ovh
ovh:
  service_name: ns3156789.ip-51-83-6.eu  # garde l'IP publique pour les API
                                          # mais SSH passe par le mesh
----

==== 3. Inscription automatique au bootstrap

Pendant le `beryl bootstrap`, mfsBSD-in-QEMU :

. Pose le binaire Tailscale FreeBSD (`pkg install tailscale` ou
  port `net/tailscale`).
. Pose une pre-auth-key Headscale dans `/usr/local/etc/tailscale-auth.key`
  (générée via API Headscale par beryl, expirable, single-use).
. Configure rc.conf : `tailscaled_enable=YES`,
  `tailscale_up_args="--auth-key=$(cat /usr/local/etc/tailscale-auth.key) --hostname={{ hostname }}"`.
. Au premier boot FreeBSD, le serveur s'inscrit tout seul dans le
  mesh, reçoit son IP `100.64.X.Y`.

==== 4. Recettes beryl associées (futures)

* `headscale-server` : pose Headscale (binaire + config + cert TLS
  via Let's Encrypt) sur un host dédié.
* `tailscale-client` : pose le client Tailscale FreeBSD sur les
  hosts gérés par beryl, avec auth-key beryl-générée.
* `firewall-pf-tailscale` : règles pf qui ne laissent passer SSH /
  Tang / autres services internes que sur l'interface
  `tailscale0` (`100.64.0.0/10`), bloquent tout depuis les
  interfaces publiques.

=== Questions ouvertes à trancher

* *Où vit le serveur Headscale ?* NAS interne Aloli, VPS dédié,
  plusieurs en HA ? Dépend de la criticité (si Headscale tombe,
  les nouveaux serveurs ne peuvent plus joindre le mesh, mais les
  serveurs déjà inscrits continuent à parler entre eux via
  WireGuard direct grâce au key-relay déjà en place).
* *Tang en HA via Headscale* : on peut avoir 3 Tangs sur 3 IPs
  Tailscale différentes, tous joignables via le mesh. Cohérent
  avec `crystal-clevis-zfs` v0.2.0 SSS multi-Tang.
* *Pre-auth-key vs OAuth-style* : Headscale supporte plusieurs
  modes d'authent. Pour beryl, pre-auth-key single-use posée au
  bootstrap est probablement le plus simple. Renouvellement
  d'auth via API Headscale après expiration.
* *Bootstrap FreeBSD-15 et `if_wg`* : à vérifier que le kernel
  module est inclus par défaut dans la distrib mfsBSD-SE qu'on
  utilise. Sinon, charger via `loader.conf` ou recette dédiée.
* *Compatibilité QEMU NAT pour les tests* : le mesh WireGuard
  doit pouvoir traverser le NAT user-mode de QEMU. Tailscale a
  un mécanisme DERP (relay) qui devrait gérer. À valider sur
  le banc QEMU.
* *Plan de bascule pour les serveurs déjà déployés* : ajouter
  Tailscale via une recette `apply` post-installation. Pas de
  re-bootstrap nécessaire si Headscale est en place après coup.

=== Impact sur les ADR

Plusieurs ADR à venir :

* *Couche réseau Aloli* : décrit la topologie Headscale (control
  plane, exit nodes éventuels, ACLs).
* *Sécurité par défaut* : SSH et Tang fermés sur les interfaces
  publiques, ouverts seulement sur `tailscale0`. À intégrer dans
  les recettes `firewall-pf` et `ssh-hardening`.
* *Bootstrap headless* : l'inscription automatique au mesh devient
  une étape standard du `beryl bootstrap`, à documenter dans
  ADR-013 (no-chroot post-install) ou un nouvel ADR dédié.

=== Couplage avec les décisions actées

* *Option D (Tang)* : Headscale rend l'Option D *opérationnellement
  praticable* sans exposer Tang publiquement. C'est probablement le
  prérequis qui manquait pour faire de l'Option D le défaut Aloli.
* *Q11.2 (groupes de hosts)* : un groupe peut hériter d'une
  configuration Headscale (tag Tailscale = nom du groupe pour les ACL).
* *Note mémoire `feedback_beryl_no_root_ssh.md`* : Headscale
  renforce ce principe (root SSH désactivé partout, et même les
  accès admin via Tailscale sont en `admin` + sudo).

=== Effort estimé

* *Headscale en service stable* : 1 jour de déploiement (binary
  Headscale, config, TLS, DNS) + tests.
* *Recette `tailscale-client`* : 0.5 jour.
* *Adaptation `beryl bootstrap` pour pre-auth-key* : 0.5 jour.
* *Tests bout-en-bout sur banc QEMU* : 0.5 jour.

Total ~3 jours, à programmer après que la stratégie multi-niveaux
des recettes (Q6.1) soit tranchée — la recette `tailscale-client`
relèvera de la stratégie commune ou Aloli-spécifique selon les
décisions.
