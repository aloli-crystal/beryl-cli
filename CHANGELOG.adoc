== [Non publié]

=== Convention `--dry-run` / `--apply` unifiée (BREAKING)

Toutes les commandes qui MODIFIENT (config, API, serveur) sont désormais en
**dry-run par défaut** et exigent **`--apply`** pour agir — une seule façon
de faire. Avant, la plupart appliquaient par défaut avec `-n/--dry-run` pour
prévisualiser ; ces flags (et `--check`) sont supprimés.

* Commandes basculées : `add-domain`, `add-provider`, `apply`, `boot-hd`,
  `bootstrap`, `dns`, `dns-alias`, `headscale-authkey`, `init`, `lock`,
  `reboot`, `rescue`, `scaleway-reinstall`, `tang-enroll`, `unlock`, `wipe`,
  `scan`.
* `scan` : `--write`/`-w` remplacé par `--apply` (écrit le host.yml au
  chemin auto) ; `--write-to` implique `--apply`.
* Les suggestions « pour exécuter » ajoutent `--apply` (au lieu de retirer
  un flag de preview).
* Déjà conformes, inchangées : `os-upgrade`, `pkg-ops`.

=== `scan --dns` / `beryl dns` : retrait du renommage OVH (displayName)

L'étape « rename panel » (best-effort, qui forçait le `displayName` OVH au
FQDN) est supprimée du cœur partagé `DnsApply`. Inutilisée, et
contre-productive : elle écrasait les noms courts du panel (adi, bacca…) que
`scan --discover` lit désormais pour nommer les host.yml. Code mort retiré au
passage (`update_display_name`, `set_display_name`, champ
`Plan.current_display_name`). Les renames Dedibox/Scaleway (mécanismes
propres, `update_hostname` / nom serveur) sont conservés.

=== Fix : les dossiers de service ne sont plus pris pour des domaines

`Loader.load_domains` ne retient un sous-dossier de société comme domaine
que s'il **contient un point** (un domaine est un FQDN). Les dossiers de
service (`recipes`, `info`, …) n'en sont plus considérés — `beryl scan
--discover <société>` et les commandes ciblant un domaine ne listent plus
`recipes`/`info` par erreur. Aucune liste d'exceptions à maintenir.

=== `scan --discover` : choix du domaine cible quand il y en a plusieurs

Un seul domaine → choisi d'office. Plusieurs → `--domain` s'il est fourni,
sinon on le DEMANDE interactivement (liste numérotée), ou on REFUSE en
`--non-interactive` (avec la liste) pour rester scriptable.

== [0.6.0] - 2026-07-12

=== `beryl apply` — nouvelles primitives et variable `{{ public_ip }}`

* Primitives : `poudriere-build` (dépôt pkg auto-suivi par ABI), `directory`,
  `symlink`, `mariadb-secure`, `github-ssh-key`.
* Variable de recette `{{ public_ip }}` : l'IPv4 publique de l'hôte (champ
  `ovh.ipv4`), pour binder un service public sans coder l'IP en dur (ex.
  `listen {{ public_ip }}:443`). Absente (échec explicite `UnknownVariable`)
  si l'IP publique n'est pas connue.

=== `beryl os-upgrade` — mode flotte

Accepte une portée `société|domaine|host` (plus seulement un host) et met à
jour tout le périmètre. Résumé de flotte en tableau lisible, connexions
fail-fast, et remontée du vrai motif quand `freebsd-version` revient vide.

=== `beryl wipe` — effacement sécurisé

* `--sanitize` : `blkdiscard --secure` (effacement cryptographique du SSD).
* `--verify` : relecture de zéros après effacement.
* Un log horodaté par disque, en parallèle.

=== Connexions SSH — cascade des utilisateurs

`connect_users` : cascade d'utilisateurs SSH pour la connexion (défaut
`connect_user`, puis root). Notes de flotte plus claires.

=== Qualité — conformité ameba

beryl passe désormais ameba en CI (fin de l'exclusion) : `.ameba.yml` commun
de l'écosystème, étape linter `bin/ameba`, et correction des 23 infractions
historiques.

=== Logs — numéro d'étape

Préfixe `[Étape N]` lisible dans les logs.

=== `beryl scan --discover` : découverte de parc OVH

Nouvelle capacité de découverte : `beryl scan --discover <société>` (ou
`--account=<société>`) liste les serveurs dédiés OVH du compte via l'API
(SANS SSH ni rescue), repère ceux absents de la config, et écrit un
`host.yml` MINIMAL pour chacun sous `~/.config/beryl/<société>/<domaine>/`.

* Contenu du squelette : `provider: ovh` + bloc `ovh:` (service_name,
  gamme, rack, IPv4, IPv6, prix/mois) — métadonnées récupérées par l'API.
* Nom du fichier : le `displayName` OVH nettoyé (ex. « adi » →
  `adi.host.yml`), sinon un placeholder `new-<ns…>` à renommer.
* N'écrase jamais un `host.yml` existant ; `--dry-run` pour prévisualiser.
* Disques/ZFS/hardware restent à compléter ensuite via
  `beryl scan <host> --write` en mode rescue.
* Nouvelles méthodes du provider OVH : `dedicated_server_names`,
  `ipv6_block`, `server_display_name`.

=== Provider Gandi (DNS)

Nouveau provider `gandi` (capability `:dns` uniquement), pour les
domaines dont la zone DNS est gérée chez Gandi (compute ailleurs,
ex: serveurs OVH). S'appuie sur un nouveau shard `api-gandi` (client
Crystal pur de l'API Gandi LiveDNS v5, auth Personal Access Token,
upsert idempotent via `PUT`).

* `Beryl::Providers::Gandi` : `ensure_record` (A/AAAA/CNAME/TXT…),
  `refresh_zone` (no-op — Gandi propage seul), `set_reverse` lève
  (le PTR relève de l'hébergeur du bloc d'IP, pas de Gandi).
* Credentials : `GANDI_PAT` (token avec la permission Gandi
  « Gérer la configuration technique des domaines » — celle qui couvre
  les enregistrements DNS).
* Dépendance : `api-gandi` (à pousser sur `aloli-crystal/api-gandi`
  puis basculer la dépendance `path:` → `github:`).

== 0.4.0 (13 mai 2026)

=== Headscale Phases 2 → 4 — 5 nouvelles primitives + flag `--transport overlay`

Suite directe de la v0.3.0 (qui livrait `beryl env` pour les
credentials chiffrés par société). v0.4.0 livre tout le code beryl
restant pour le déploiement Headscale décrit dans la roadmap interne
`roadmap_beryl_headscale.md`. Les recettes correspondantes vivent
côté `aloli-crystal/beryl-recipes`.

==== 5 nouvelles primitives

* `headscale-join` (Phase 2) — joint un host au mesh via
  `tailscale up --login-server=URL --authkey=KEY`. Idempotent
  (`tailscale status` exit 0 → skip). La clé d'auth est lue depuis
  une variable d'env (`authkey_env_var: HEADSCALE_AUTHKEY`) côté
  beryl, jamais sur la ligne de commande de la recette. Stderr
  potentiellement leaké est masqué (substitution `[REDACTED]`).
* `assert-env-var` (Phase 3) — refuse la suite de la recette si une
  variable d'env (côté beryl, poste opérateur) est absente ou vide.
  Use case : forcer `BERYL_REASON='...'` avant un changement
  sensible.
* `assert-tailscale-up` (Phase 3) — refuse la suite si l'interface
  `tailscale0` du host cible n'est pas UP ou si la session est trop
  récente (`min_uptime_seconds`, défaut 30). Garde-fou avant la
  bascule en `sshd-overlay-only`.
* `auto-close-schedule` (Phase 3) — pose un `at +Nh` qui rejoue une
  autre recette sur ce même host (typiquement
  `sshd-public-close`). Idempotent : un job déjà posé sous le même
  `tag:` est remplacé. Le tag distingue plusieurs fenêtres
  concurrentes.
* `headscale-state-commit` (Phase 3) — append une ligne au fichier
  `audit.log` du repo `aloli/headscale-state` puis
  `git add && commit && push`. Sérialisé via `flock`. Pré-requis :
  recipe `headscale-backup` déjà appliquée (repo cloné sur le host).

==== Extension de `sshd-config-set` : `value_from_command`

`sshd-config-set` accepte désormais `value_from_command:` (mutuellement
exclusif avec `value:`). La commande est exécutée côté serveur cible,
son stdout strippé devient la valeur de la directive. Cas d'usage
principal : la recette `sshd-overlay-only` qui doit poser
`ListenAddress <ip-tailscale>` sans connaître cette IP à l'avance.

==== Phase 4 — flag global `--transport=public|overlay`

Nouveau flag global du CLI `beryl` (avant la sous-commande) qui
bascule la résolution de `ssh_host` pour tous les sous-commandes qui
font SSH :

  beryl --transport=overlay apply loulou.aloli.net

Quand `--transport=overlay` est actif ET que le host a un champ
`overlay_ip:` dans son YAML (typiquement `100.64.0.5`), c'est cette
IP qui est utilisée pour la connexion SSH au lieu du FQDN public.
Pas de fallback automatique (le flag dit explicitement "via mesh") ;
si `overlay_ip` est absent, on retombe sur la résolution publique
normale.

`ResolvedHost#overlay_ip` est exposée pour les tests et debug.

==== Tests

* +20 examples (4 par primitive, 4 sur le switch transport_mode).
  Total : 330 examples, 0 failures.
* Le couplage `ResolvedHost#ssh_host` × `Beryl.transport_mode` est
  validé par les tests unitaires du switch + tests d'intégration
  manuels (les recettes Headscale tournant sur des hosts FreeBSD).

== 0.3.0 (13 mai 2026)

=== `beryl env` — credentials chiffrés par société

Les credentials providers (`OVH_APPLICATION_KEY`, `SCW_SECRET_KEY`,
`DEDIBOX_TOKEN`...) vivaient dans `~/.config/beryl/.env.yml`, plat
à la racine, en *clair*. Une fuite (backup non chiffré, sync iCloud
mal configurée, `git add` malheureux) exposait toutes les clés de
toutes les sociétés d'un seul coup.

v0.3.0 introduit un *coffre chiffré par société*, à côté du dossier
de chaque société :

[source]
----
~/.config/beryl/
├── _default.yml
├── aloli/
│   ├── _account.yml
│   ├── .env.toml.age              ← coffre aloli, TOML chiffré age
│   ├── aloli.fr.yml
│   └── ...
└── quimeo/
    ├── .env.toml.age              ← coffre quimeo, indépendant
    └── ...
----

Format plaintext du coffre (avant chiffrement, via
`aloli-crystal/secrets`) :

[source,toml]
----
[ovh]
OVH_APPLICATION_KEY = "xxx"
OVH_APPLICATION_SECRET = "yyy"
OVH_CONSUMER_KEY = "zzz"

[scaleway]
SCW_SECRET_KEY = "abc"
----

==== Nouvelles sous-commandes

* `beryl env migrate [--purge-yaml] [<société>...]` — convertit
  `.env.yml[<société>]` en `<société>/.env.toml.age`. Refuse si le
  coffre existe déjà (sauf `--force`). `--purge-yaml` supprime la
  section migrée du fichier source après écriture du coffre. Sans
  argument, migre toutes les sociétés présentes.
* `beryl env edit [--create] <société>` — décrypte le coffre, lance
  `$EDITOR` sur un tempfile mode 0600 (suffixe `.toml`), valide le
  TOML, re-chiffre. Le coffre reste intact si l'éditeur sort
  non-zéro ou si le TOML édité est invalide. `--create` permet de
  partir d'un squelette vide.
* `beryl env show <société>` — affiche le plaintext (debug local,
  à éviter en production — préférez `beryl env edit`).

Alias court : `beryl e`.

==== Intégration loader

`Beryl::Config::Loader.load` charge désormais, après le YAML racine,
chaque `<société>/.env.toml.age` détecté. Le coffre *remplace* la
section homonyme du `.env.yml` (le coffre fait autorité), ce qui
permet une migration progressive — tant qu'une société n'a pas
migré, son fragment du `.env.yml` continue d'être lu sans changement.

==== Dépendance

* Nouvelle dépendance : `aloli-crystal/secrets ~> 0.5` (utilise
  `Secrets::Vault.encrypt/decrypt`, `Secrets::Editor.edit`,
  `Secrets::Recipients.encryption_keys`, `Secrets::MasterKey.read`).
* Pré-requis opérateur : `secrets init` une première fois sur le
  poste (génère la master key + paper recovery).

==== Multi-recipients (équipe)

Le coffre est chiffré au roster `Secrets::Recipients.encryption_keys`,
qui est aujourd'hui *global* (`~/.config/secrets/recipients.toml`).
Un roster par société viendra quand le module amont acceptera un
chemin override — vous pourrez alors limiter chaque coffre à
l'équipe correspondante (la team `quimeo` n'aura pas la master key
qui ouvre `aloli/.env.toml.age`).

==== Tests

+9 examples sur les fonctions pures du chiffrement
(`parse_vault_toml`, `serialize_account_to_toml`, round-trip,
échappement, set/clear). Le test d'intégration `Loader` reste
manuel — la constante `Secrets::CONFIG_DIR` est résolue à l'init
du module et rend fragile un mocking de la master key au runtime.

=== `beryl apply` — moteur de recettes (Phase 1, PoC)

Réécriture de `beryl apply` selon l'architecture à 2 niveaux du
document de design `apply-recipes-architecture.adoc` : des
*primitives* Crystal natives idempotentes orchestrées par des
*recettes YAML* reliées par un champ `requires:`.

* *Avant* : `apply` monolithique qui synchronisait
  `packages` / `sudoers` / `users` lus directement du YAML host.
* *Après* : `apply` scanne le dossier d'orchestration du host
  (`<config>/<société>/<domaine>/<host>/`), résout les `requires:`
  (récursif + tri topologique + détection de cycle, override
  dossier host prioritaire sur le dépôt central), puis exécute les
  `steps:` via SSH avec un rapport final
  « N étapes : X skipped, Y applied, Z failed ».

[CAUTION]
====
*Rupture de comportement* : l'ancienne synchronisation
packages/sudoers/clés SSH directe est retirée. Ces capacités
reviennent en Phase 2 sous forme de primitives
(`user-update-keys`, `sysrc-set`, …) et de recettes Aloli.
====

==== Code

* Nouveau module `Beryl::Apply` (`src/beryl/apply/`) :
** `Shell` / `SshShell` — abstraction du transport SSH (injectable
   en test via `FakeShell`).
** `Primitive` + registre + `pkg-install` (idempotente :
   `pkg info` avant action, installe le delta).
** `Recipe` / `Step` — parsing + validation (`recipe:` ==
   nom de fichier).
** `Resolver` — fermeture transitive des `requires:`, tri
   topologique (Kahn), détection de cycle, override par dossier
   host.
** `Executor` — déroulé des steps, interpolation `{{ var }}`
   scalaire, rapport agrégé. Stop net sur erreur.
* `beryl apply` accepte `--check` comme synonyme de `--dry-run`.
* Le bloc `recipes:` (`local_path`) du merge pointe le dépôt
  central de recettes (défaut `<config>/recipes`).
* Recettes PoC livrées dans `aloli-crystal/beryl-recipes`
  (`base-packages`, `shell-tools`, `freebsd-updates`,
  `post-install`).

==== Phase 2 — couverture des primitives

Jeu complet des primitives de la section 7 du doc de design, chacune
idempotente (lecture d'état réel avant action) et testée :

* `pkg-remove` — `pkg delete` du delta présent.
* `service-enable` / `service-disable` — `sysrc <svc>_enable` +
  `service start`/`stop` (état lu via `sysrc -n` + `onestatus`).
* `sysrc-set` — variable `/etc/rc.conf` (skip si `sysrc -n` déjà à la
  cible).
* `file-write` / `file-template` — écriture idempotente (SHA-256) avec
  `mode`/`owner` vérifiés via `stat`.
* `user-create` — `pw useradd` (skip si `pw show` trouve l'utilisateur).
* `user-update-keys` — synchro `authorized_keys` (set, comparaison
  type+blob). *Garde-fou* : refus de retirer la clé que beryl utilise
  pour se connecter (dérivée de `identity_file` via `ssh-keygen -y`,
  portée par `Context`).
* `sshd-config-set` — directive dans `sshd_config.d/beryl.conf`,
  validée (`sshd -t`) et `service sshd reload` si changement.
* `pf-rule` — règle dans un bloc géré de `/etc/pf.conf`, validée
  (`pfctl -nf` sur fichier temporaire) avant bascule + `pfctl -f`.
* `cron-entry` — ligne dans un bloc géré de la crontab d'un user.

Ajustement : `Beryl::Apply::Context` transmis aux primitives (porte les
clés protégées) ; `Primitive::PrimitiveError` (param manquant,
garde-fou) traité comme step `failed` (stop net).

== 0.2.2 (8 mai 2026)

=== Migration XDG Base Directory

Beryl respecte désormais la
https://specifications.freedesktop.org/basedir-spec/basedir-spec-latest.html[spec
XDG Base Directory] pour la racine de configuration.

* *Avant* : `~/.beryl/` (non-XDG, posait souci côté Linux où
  `~/` accumule trop de dotfiles non standardisés).
* *Après* : `$XDG_CONFIG_HOME/beryl/` si la variable est
  définie, sinon `~/.config/beryl/` (défaut XDG).

[CAUTION]
====
*Migration manuelle requise* : pas de fallback automatique vers
l'ancien chemin (cohérent avec « pas de défauts silencieux »
côté Aloli). Si vous avez un `~/.beryl/` existant :

[source,shell]
----
mv ~/.beryl ~/.config/beryl
----

Sans cette commande, beryl démarre sur un Root vide et toutes
les sociétés/hosts sont introuvables (« société inconnue »).
====

=== Code

* Nouveau helper `Beryl::Xdg.config_dir` (`src/beryl/xdg.cr`)
  qui résout dynamiquement la racine au runtime (honore
  `$XDG_CONFIG_HOME`).
* `Beryl::CLI::DEFAULT_CONFIG_ROOT` (constante) → méthode
  `Beryl::CLI.default_config_root`.
* `Beryl::Config::Root::DEFAULT_PATH` (constante) → méthode
  `Beryl::Config::Root.default_path`. Le paramètre `path` de
  `Root.load` accepte désormais `nil` (pris au défaut au moment
  de l'appel, pas à la définition).
* `Beryl::Config::EnvFile::DEFAULT_PATH` → méthode
  `Beryl::Config::EnvFile.default_path`. Idem `path` accepte
  `nil`.
* Tous les commentaires inline et docs (`*.adoc`, README,
  scripts shell, qemu/) mis à jour vers `~/.config/beryl/`.

=== Tests

242 specs unitaires verts. Fixture `spec/beryl/cli/scan_spec.cr`
alignée sur `/tmp/.config/beryl` (cohérence avec la nouvelle
convention).

=== Convention de nommage Aloli

* *Rename du repo `crystal-beryl` → `beryl`*. Tous les shards
  Aloli abandonnent le préfixe `crystal-` (cf. note mémoire
  `feedback_naming_shards_api_aloli`). GitHub redirige les
  anciennes URLs.
* *Factorisation des packages API* : les shards distants
  `crystal-api-{ovh,scaleway,dedibox,hetzner}` deviennent
  `api-{ovh,scaleway,dedibox,hetzner}` côté repo *et* côté
  champ `name:` du shard.yml. Beryl s'aligne :
  `dependencies.api-ovh:` (au lieu de `ovh-api:`),
  `require "api-ovh/ovh_api"` (au lieu de `require "ovh-api/ovh_api"`).
  Les modules Crystal restent inchangés (`OvhApi::Client`,
  `ScalewayApi::Client`, `DediboxApi::Client`).

=== Chiffrement des données (Options C + D)

* *Module `Beryl::Encryption`* : génération + lecture de clé hex
  256 bits, chmod 0400, anti-écrasement, scrub.
* *`Pool#encryption: EncryptionConfig?`* (anciennement Bool).
  Struct supportant les modes `ssh_unlock` (Option C, clé sur
  poste opérateur) et `tang` (Option D, auto-unlock via Tang au
  boot). Factory `from_yaml` rétrocompatible
  (`encryption: true` → `mode: ssh_unlock`).
* *Commande `beryl unlock`* : route par mode. ssh_unlock = clé
  locale via stdin SSH (inchangé). tang = délègue à
  `crystal-clevis-zfs unlock` côté serveur. Pre-flight binaire
  serveur en mode tang.
* *Commande `beryl reboot`* : `--soft` (SSH) ou `--hard` (API
  hébergeur), enchaîne `unlock` automatiquement après le reboot
  si pools chiffrés.
* *Commande `beryl status`* : état pools (ONLINE/ABSENT/LOCKED/
  DEGRADED) + services (sshd, cron, custom via -S).
* *Commande `beryl tang-enroll`* : bascule Option C → Option D.
  Push clé locale via stdin SSH dans tmpfs, change keylocation,
  appelle `crystal-clevis-zfs bind --use-existing-key`, cleanup
  inconditionnel via ensure, met à jour `/etc/rc.conf` via
  `sysrc` (idempotent).

=== Post-install sans chroot et conf FreeBSD par YAML (21 avril 2026)

==== Ajouté

* ADR-013 — *post-install sans chroot.* Le chroot `bsdinstall` déclenche
  un `SIGSYS` Capsicum sur `pkg install` (vérif de signature tuée par le
  sandbox). `beryl` ne l'utilise plus : l'installerconfig est devenu un
  préambule `ZFSBOOT_*` + `DISTRIBUTIONS=` seul, tout le post-install
  (users via `pw -R /mnt`, packages via `pkg -r /mnt`, rc.conf,
  timezone, sudoers) est piloté par mfsBSD hors chroot en ciblant
  explicitement `/mnt/`. Validé bout-en-bout sur `loulou.aloli.net`.
* `Beryl::Bootstrap::UserSpec` : record décrivant un user à créer
  (name, primary_group, secondary_groups, shell, ssh_keys) avec
  `validate!` + `to_tsv` pour le driver shell.
* `Beryl::Bootstrap::QemuInRescue.new` accepte désormais
  `disks : Array(String)`, `raid`, `users`, `packages`, `sudoers`
  (multi-disque et RAID ZFS stripe/mirror/raidz{,2,3}).
* Template `rescue-run-vm.sh` : driver shell complet qui fait tourner
  QEMU via `systemd-run --unit=qemu-vm` (survit à la déconnexion ssh),
  pilote mfsBSD en SSH, fait le post-install, puis `poweroff`.
* `beryl boot-hd <host>` : bascule un hôte OVH en boot disque via
  l'API (inverse de `rescue`). Utilisé en interne par `bootstrap` après
  le `poweroff` de la VM, disponible aussi en CLI.
* `beryl wipe <host> --disk=PATH` : wipe destructif (zpool destroy +
  labelclear + sgdisk --zap-all + dd zéros). Demande confirmation
  `OUI`/`YES`. Pour ré-installer sur un disque qui porte déjà un pool
  BSD (garde-fou NOGO de `beryl bootstrap`).
* `Beryl::FreebsdConfig` + `Beryl::UserSpecYaml` : parser du bloc
  `freebsd:` de l'inventaire YAML. Champs : hostname, timezone,
  pool_name, swap_gb, disks, raid, install_type, users, packages,
  sudoers. Valide `raid ∈ {stripe, mirror, raidz, raidz2, raidz3}` et
  `install_type ∈ {distribution_sets, packages}` à la lecture
  (ArgumentError sinon, pas de défaut silencieux).
* `beryl bootstrap <host>` lit `freebsd:` de l'inventaire quand il est
  présent. Priorité : flag CLI > YAML > défaut MVP > erreur explicite.
  Un `--disk` / `freebsd.disks` manquant déclenche une erreur claire
  avant toute action destructive.
* 13 nouveaux specs pour `FreebsdConfig` et son intégration dans
  `Inventory`. Total : 83 specs verts.
* `examples/inventory.yml` : bloc `freebsd:` ajouté à `web01.aloli.fr`
  et exemple complet (`loulou.aloli.net`) avec users, packages, sudoers.

=== Pivot bootstrap — ADR-010 / ADR-011 (avril 2026)

Le test grandeur nature du 19 avril 2026 sur un Kimsufi OVH UEFI-only
a révélé que l'ISO mfsBSD `dd`-ée n'est pas amorçable par un firmware
UEFI (ADR-010). Le test manuel du 20 avril a validé end-to-end la
voie de remplacement : FreeBSD est désormais installé *depuis* le
rescue Linux via une VM QEMU en passthrough disque (ADR-011).

==== Ajouté

* `Beryl::Bootstrap::QemuInRescue` : classe unifiée qui remplace le
  couple `MfsBSD` + `Installer`. Orchestre apt → ISO → remasterisation
  xorriso → OVMF → QEMU (-no-reboot, UEFI, KVM, passthrough disque)
  → `reboot -f` → attente SSH.
* Template `templates/installerconfig.sh` : format bsdinstall en deux
  parties (variables ZFSBOOT + distributions pkgbase, puis post-install
  chroot pour `rc.conf` en `ifconfig_DEFAULT`, `fstab` en labels GPT,
  users `admin`/`deploy`, sudoers wheel NOPASSWD, clé SSH, poweroff).
* CLI `beryl bootstrap` : nouveau flag `--iso-url` et
  `--freebsd-version`, et `--installed-user` (défaut `admin`,
  `PermitRootLogin no` respecté).
* Specs : 24 nouveaux specs pour `QemuInRescue` (render, base64, qemu
  command line, argument validation). Total : 54 specs verts.
